# Ticket Center 面试 100 问

## 01｜项目定位与架构设计

- [ ] **Q1：你先介绍一下 Ticket Center。**

Ticket Center 是一个演出票务预约项目，用户可以浏览活动、抢票，也可以在售罄后加入候补。我主要想解决的不是简单的订单增删改查，而是**很多人同时抢有限的票，系统还不能超卖、重复下单或者丢掉已经受理的请求**。所以入口用 Redis Lua 做预扣，预约和恢复任务存到 MySQL，再通过 RabbitMQ 异步创建订单。支付目前是模拟流程；这个项目更值得展开的是并发正确性和故障恢复。

- **做什么**：演出票务预约，包含抢票、异步建单、模拟支付、取消和候补。
- **难在哪**：库存有限，还要处理重复请求、消息重试和中途故障。
- **怎么做**：Redis 快速准入，MySQL 保证交易约束，任务表和 MQ 推进异步流程。

- [ ] **Q2：项目解决了什么问题？业务范围有多大？**

我会把它分成两部分：一部分是让用户找到活动，包括详情、附近活动和评价；另一部分是把票安全地卖出去，包括库存、订单、积分抵扣和候补。比如一场活动只剩一张票，多个用户同时提交时，最终只能有一个有效订单；占票后不支付，还要把资源释放给别人。**这条交易闭环是项目的重点**。它目前不是已经商业运营的售票平台，也没有接入真实支付渠道。

- **交易闭环**：浏览 → 预约 → 建单 → 支付或取消，售罄后可以候补。
- **配套功能**：验证码登录、评价、关注、签到积分、附近活动和 UV。
- **项目边界**：学习与工程实践项目，不虚构生产用户量和真实支付接入。

- [ ] **Q3：为什么拆成这几个模块？**

拆分时我更看重业务关系，而不是把每张表都拆成服务。用户和活动偏展示与互动，订单、库存、积分则需要一起保证一致性，所以我把后者留在同一个服务、同一个数据库里。这样创建订单时，扣库存、扣积分、写订单可以用一个本地事务完成。**展示域和交易域可以独立演进，但没有把强关联的交易操作拆散**，避免为了微服务引入不必要的分布式事务。

- **业务拆分**：核心服务管理用户、活动与互动；订单服务管理交易。
- **事务边界**：库存、订单、预约、积分和恢复任务保留在同一个交易库。
- **配套模块**：Gateway 做路由，公共模块复用基础能力，Vue 承担前端展示。

- [ ] **Q4：这个规模为什么用微服务，而不是单体？**

如果只按当前业务规模判断，我不会说微服务是必需的，模块化单体反而更省维护成本。这个项目采用服务拆分，也有练习分布式工程能力的目的，比如服务间怎么认证、跨服务调用失败怎么办、哪些数据应该放在同一个事务里。我的取舍是只拆出相对清晰的核心域和交易域，**不为了技术栈丰富而把库存、积分、订单继续拆开**。如果是资源有限的真实团队，我会先评估单体方案。

- **承认取舍**：当前规模下，模块化单体完全可以实现这些业务。
- **实践目标**：训练服务边界、跨服务鉴权、服务发现和独立部署。
- **实际成本**：网络故障、配置管理、调用延迟与排障复杂度。

- [ ] **Q5：一个请求从浏览器到数据库经过哪些层？**

拿查询个人订单来说，浏览器先把 Token 放到请求头里，经过网关到订单服务。服务端拦截器根据 Token 从 Redis 取用户身份，确认登录后再进入业务代码。Controller 负责接参数，Service 组织查询条件，Mapper 执行 SQL。这里我会特别强调两点：**用户身份不能直接相信前端传的 userId，查订单还要带当前用户条件**；请求完成后也要清掉 ThreadLocal，防止线程复用时串用户。

- **入口**：浏览器携带 Token，Gateway 路由到业务服务。
- **身份**：拦截器读取 Redis 会话，校验权限，设置当前线程的用户信息。
- **业务**：Controller 接参，Service 执行业务，Mapper 访问数据库；结束后清理用户上下文。

- [ ] **Q6：服务拆分后，用户和活动数据怎么关联？**

订单库里会保存用户和活动的关联 ID，但不会直接去操作核心服务的表。需要活动信息时通过服务接口获取，交易必须稳定的字段则保存快照。比如用户受理时确认的票价是 200 元，消息稍后才被消费，不能因为管理员期间改了价格，就按新价格给他建单。**关联 ID 解决“是谁”，交易快照解决“当时按什么条件成交”**，这两个作用不一样。

- **关联方式**：保存 userId、eventId 等标识，跨服务需要时通过接口查询。
- **交易快照**：预约记录受理时的票价与抵扣选择，不在消费时随意重新定价。
- **边界意识**：跨服务逻辑关联不等于跨库外键，也不直接复用对方 Mapper。

- [ ] **Q7：为什么活动详情不把票档和积分都一次返回？**

最初如果把所有信息都塞进详情接口，哪怕活动介绍命中了缓存，也可能还要跨服务查票档或积分，这样缓存的收益就被抵消了。现在把稳定的活动详情和动态的交易信息分开，公共缓存也不会混入某个用户的个人状态。代价是前端要多发请求，所以我会同时看页面加载体验。**这项优化证明的是详情接口的热点路径更轻，不是整个页面的开销全部消失了。**

- **变化频率不同**：活动介绍相对稳定，库存和个人积分变化更频繁。
- **热点路径瘦身**：详情缓存命中时不再额外查订单域，票档等数据单独请求。
- **衡量完整体验**：详情接口更快，不代表整页同比例更快。

- [ ] **Q8：Nacos 在项目中做什么？本地和 cloud 配置有什么区别？**

Nacos 在这里主要负责服务注册发现和配置管理。本地开发时可以直接填目标服务的 URL，减少启动依赖；部署多实例时，再通过服务名发现实例。实际部署很容易踩的一个坑是注册地址：如果注册的是只有容器内部才能访问的 IP，注册成功也不代表别人能调通。**注册中心解决的是“去哪里找服务”，并不自动解决限流、熔断和整个系统的高可用。**

- **服务发现**：cloud 模式按服务名找实例，网关可以使用负载均衡路由。
- **配置管理**：环境配置集中管理；本地调试可以直接指定服务地址。
- **部署注意**：注册地址必须跨机器可达，接入 Nacos 不等于自带熔断和容灾。

- [ ] **Q9：项目中最有技术含量的三个点是什么？**

我会重点讲三个点。第一个是防超卖，不是简单加一把分布式锁，而是把入口限流量和最终数据约束分开。第二个是异步建单的恢复：消息发送失败、重复消费、取消时 Redis 不可用，都需要有后续处理的依据。第三个是热点路径优化，比如让售罄请求在进入数据库事务前返回，详情缓存命中后减少跨服务查询。**每个点我都希望能讲清楚为什么这么改、怎么验证，以及还有什么没覆盖。**

- **并发正确性**：Lua 预扣、数据库条件更新和唯一约束各有职责。
- **异步恢复**：预约与任务一起保存，重试、幂等和补偿形成闭环。
- **性能优化**：说明瓶颈、修改和验证，不只罗列中间件名称。

- [ ] **Q10：简历上的性能数字应该怎么解释才经得起追问？**

我会先交代场景，避免数字看起来很大但口径不清。这组数据来自项目的历史本地压测：预约入口稳态从大约 223 提到 728 QPS，但里面包括售罄和重复请求被正常拒绝，**不是每秒成功生成 728 个订单**。详情接口优化后约为 2511 到 3584 QPS，轮次之间有明显波动。除了吞吐，还要核对 50 张票最终是否只产生 50 个有效订单，库存有没有扣错。这些数据不能直接外推成生产上限。

- **预约入口**：历史稳态约 223 → 728 QPS，包含成功受理和预期业务拒绝。
- **详情接口**：历史稳态约 1376 → 2511–3584 QPS，只代表该接口。
- **交代条件**：本地 JMeter、Docker Desktop、Gateway、多轮测试；不是生产容量承诺。

## 02｜登录、安全与前后端边界

- [ ] **Q11：验证码登录的完整流程是什么？验证码能重复使用吗？**

用户先申请验证码，服务端会检查发送频率，不能让同一个手机号一直刷。登录时我不会先 GET 验证码、在 Java 里比较后再 DEL，因为两个请求可能同时读到正确验证码，都登录成功。这里用 Lua 把**比较和消费合成一个原子操作**，只有一个请求能成功使用。校验通过后再建立 Redis 登录会话。需要说明的是，目前实现的是验证码和会话逻辑，不是完整的商业短信发送服务。

- **发送限制**：同手机号 60 秒冷却，日窗口最多 10 次，验证码有效期 2 分钟。
- **一次性消费**：Lua 原子完成校验和删除，避免并发请求重复使用。
- **登录结果**：创建或查询用户，生成 Token，把会话放进 Redis；没有接真实短信渠道。

- [ ] **Q12：为什么不是 JWT？Redis Token 怎么失效？**

这个项目没有用 JWT，而是把随机 Token 当成会话的查询凭证。前端在 authorization 请求头直接传 Token，后端到 Redis 查用户信息，访问时刷新 10 小时有效期。这样退出登录比较直接，删掉对应会话就行，不用再单独维护 JWT 黑名单。当然它不是无状态认证，Redis 不可用就会影响登录校验。**这是用一次服务端查询，换取更直接的会话控制**；当前退出也只处理这一个 Token，不是自动踢掉所有设备。

- **实际方案**：随机 Token + Redis Hash，会话不是 JWT。
- **续期与退出**：10 小时滑动过期；退出删除当前 Token 对应的会话。
- **取舍**：服务端控制失效方便，但每次认证依赖 Redis。

- [ ] **Q13：ThreadLocal 怎么用？为什么写入顺序也重要？**

ThreadLocal 在这里主要是为了让业务层方便拿到当前用户，避免每一层都传 userId。但 Web 容器会复用线程，如果请求结束后不清理，下个用户可能读到上个请求的身份。还有一个容易忽略的点：拦截器在自己的前置处理中抛异常，不一定会执行它自己的结束回调。所以这里先完成 Redis 查询和续期，再放入用户上下文。**既要正常结束时清理，也要尽量避免异常前就留下上下文。**

- **作用范围**：当前请求线程内传递已经验证的用户信息。
- **清理要求**：请求结束必须 remove，线程池会复用线程。
- **异常顺序**：Redis 会话读取和续期成功后再设置上下文，不能只指望结束回调兜底。

- [ ] **Q14：公开接口、登录接口和管理员接口如何区分？**

我会把“能不能访问”和“有没有权限做这件事”分开。浏览公开活动不一定要求登录，下单和查个人订单需要登录，管理活动还要进一步检查管理员身份。公开规则会结合请求方法和路径，不能因为 GET 详情公开，就把同一路径下的修改操作也放开。**登录只证明你是谁，不代表你可以做所有操作**。这个项目主要用拦截器完成这些判断，不能套用成 Spring Security 的实现。

- **公开范围**：按请求方法和路径判断，不是整个 Controller 全部放行。
- **登录校验**：非公开业务接口要求有效会话。
- **管理员校验**：在登录基础上核实角色；本项目主要通过 MVC 拦截器实现。

- [ ] **Q15：如何防止用户伪造内部调用？共享内部 Token 有什么局限？**

内部接口不能因为名字叫 internal 就认为安全。这里网关会先清理外部请求携带的内部凭证，真正的服务调用再由客户端添加共享 Token，接收方也会验证。这样不会只依赖入口网关挡请求。不过，共享密钥一旦泄露，攻击者仍可能冒充服务，所以真实部署还需要限制内部端口访问、使用安全传输并做好密钥轮换。**当前做的是内部调用认证，不是每个服务都有独立身份的完整体系。**

- **外部入口**：网关移除客户端伪造的内部凭证和身份头。
- **服务之间**：Feign 添加内部凭证，接收方再次校验，不能只靠网关。
- **安全边界**：共享密钥需要保密、轮换和网络隔离，不是完整的零信任方案。

- [ ] **Q16：知道别人的 orderId 或 reservationId，能操作他的订单吗？**

不应该能。订单号只是用来定位数据，不能因为它足够长、别人难猜，就省略权限校验。比如支付和取消时，数据库更新条件会同时带订单 ID、当前用户和订单状态；查询预约也要确认归属。这样即使某个订单号出现在截图或日志里，其他用户拿到后也不能直接操作。**幂等解决“同一件事别做两遍”，归属校验解决“你有没有资格做这件事”**，两者不能互相替代。

- **防越权**：资源 ID 不是访问凭证，还要验证资源归属。
- **可信身份**：以服务端登录态中的用户为准，不信请求体里的 userId。
- **落到操作**：个人查询、支付、取消都要约束当前用户。

- [ ] **Q17：requestId 放哪里？同一个 requestId 换参数怎么办？**

假设用户点击抢票后网络超时，他不知道后台有没有受理。这时再点一次，应该重试同一个业务请求，而不是重新生成请求号，否则幂等就失效了。前端会保存 requestId、票档和是否使用积分等信息，后端再用唯一约束兜底。如果沿用同一个 requestId 却换了参数，后端会拒绝，而不是悄悄覆盖旧请求。**请求号标识的是一次业务意图，不只是一次 HTTP 调用。**

- **前端复用**：按用户和票档在 sessionStorage 保存请求号及原始选择。
- **后端约束**：用户与 requestId 唯一，同一请求不能改票档或抵扣选择。
- **请求语义**：网络重试沿用旧请求号，新的购买意图才使用新请求号。

- [ ] **Q18：Java 的 Long 传给 JavaScript 会出什么问题？金额怎么处理？**

这类问题最麻烦的是接口看起来成功了，但订单号已经在前端被舍入，后续查询就会找错数据。项目在解析响应时使用 JSONbig，把大整数保留成字符串，而不是先变成 Number 再转字符串，因为那时精度已经丢了。金额则是另一个问题，后端按分保存和计算，前端只负责展示成元。**ID 要保持原值，金额要保持运算精度**，不能把两者都简单当成普通数字处理。

- **大整数风险**：JavaScript Number 超过安全整数范围可能丢精度。
- **ID 处理**：前端使用 JSONbig，把大整数按字符串保留下来。
- **金额处理**：后端使用整数分，展示时再换算，避免用浮点数直接结算。

- [ ] **Q19：异步下单返回预约号后，前端如何避免状态错乱？**

异步下单不能让前端收到一个“成功”就直接显示出票成功。这里会先显示预约处理中，再查询预约结果，等订单真正建立后才进入待支付状态。轮询也不是简单写一个定时器：用户退出登录、切换页面，或者上一次查询很慢时，都要避免旧结果覆盖当前界面。**预约受理、订单生成、支付成功是三个不同阶段**，前后端必须用同一套业务含义展示，否则后端没丢单，用户也会以为系统出错了。

- **区分结果**：受理成功只拿到预约号，不代表订单已经创建。
- **轮询管理**：控制重复轮询，处理页面隐藏、退出登录和旧请求回包。
- **展示依据**：订单存在后才显示真实订单号与支付截止时间。

- [ ] **Q20：登录安全还存在哪些边界？能否直接说“已经支持改密踢人”？**

我会按实际实现讲，不把基础登录包装成完整的账号安全平台。项目已经有验证码限频、一次性使用和 BCrypt 存储密码，但首次设置密码跟“修改密码后所有设备退出”不是一回事。如果要支持后者，需要能找到该用户的所有会话，或者设计会话版本号，再让认证逻辑检查。**功能名称相近，不代表安全语义相同**。面试里把已完成和后续方案分开，反而更容易解释清楚。

- **已经具备**：验证码限频、一次性消费、BCrypt 密码哈希和 Redis 会话。
- **不能混淆**：首次设置密码，不等于完整的修改密码与全设备下线。
- **后续完善**：设备会话管理、密钥轮换、风险识别和验证码防刷。

## 03｜预约受理、Lua 与幂等

- [ ] **Q21：把一次预约受理逐步讲清楚。**

用户提交票档、请求号和抵扣选择后，服务端先检查这个请求是不是已经处理过，再验证售卖条件。接着用 Lua 尝试占一个名额，售罄请求在这里就可以返回。拿到名额后，还要进入数据库事务，锁库存行、检查候补优先级，把预约和恢复任务一起存下来。事务提交后才算可靠受理，后续再发消息建单。**所以接口返回预约号，是“我已经记住并会继续处理”，不是“订单已经创建完成”。**

- **前置检查**：确认登录、请求号、票档可售状态以及是否已有同一请求。
- **快速准入**：Lua 预扣库存并记录归属；随后在数据库事务中检查候补优先级。
- **可靠受理**：预约记录和建单任务一起提交，再异步推进；返回的是预约结果入口。

- [ ] **Q22：Lua 具体用了哪些数据结构？四个返回码是什么？**

单有一个库存数字不够，还得知道谁占了这张票，以及是哪一次预约占的。所以脚本同时维护库存、用户集合和预约归属。比如库存还有 1，用户第一次来就扣成 0 并写入归属；同一个预约重试时直接识别出来，不再扣第二次。返回码也刻意区分业务情况：**售罄是没票，键缺失是状态需要恢复，已经占用则可能是重试或旧状态**，后端不能统一返回“抢票失败”。

- **三个结构**：String 存余量，Set 存占用用户，Hash 存用户对应的预约归属。
- **返回含义**：0 成功或同预约重放；1 售罄；2 已有其他占用；3 库存键缺失。
- **处理区别**：缺失要初始化后重试，其他占用要结合数据库状态判断，不能都当售罄。

- [ ] **Q23：“一人一票”为什么需要 Redis、行锁和唯一索引多层保护？**

这几层不是为了把同一件事重复做三遍。Redis 面向高频请求，先把大部分售罄和重复请求拦下来；数据库行锁负责协调复杂的状态变化；唯一索引则是在异常情况下仍不允许写出两个有效订单。比如 Redis 重启后判重数据短暂不完整，也不能因此让数据库出现重复票。**缓存和锁可以减少冲突，数据库约束决定最终允许留下什么数据。**这里的一人一票，是同一用户对同一票档最多一个有效订单。

- **Redis**：快速判重和预扣，减少数据库压力。
- **行锁**：串行协调同一预约、库存和候补的状态变化。
- **唯一约束**：限制同用户同票档最多一个有效订单，作为最终数据防线。

- [ ] **Q24：requestId、reservationId、orderId 为什么不能合成一个？**

可以把它们理解成三个阶段的编号。requestId 回答的是“这是不是用户刚才那次请求”；reservationId 回答的是“后台正在处理哪次预约，这个库存是谁占的”；orderId 对应最终要支付和取消的订单。项目会提前生成订单号，但只有数据库真正建单以后，前端才应该把它当成可操作的订单。**把这些身份分开，失败时才能分清是在重试请求、推进预约，还是操作已经存在的订单。**

- **requestId**：客户端一次购买意图的重试标识。
- **reservationId**：预约流程的身份，用来追踪处理和安全补偿。
- **orderId**：最终交易实体的身份；预生成 ID 不代表订单已存在。

- [ ] **Q25：为什么把 Lua 放在数据库事务前？有没有新风险？**

抢票场景里，票卖完以后往往还会有大量请求进来。如果每个请求都先开事务、锁库存行，再发现没票，数据库会做很多无效工作。把 Lua 前移后，售罄可以在 Redis 直接返回。但这不是免费的优化：Lua 成功后如果进程崩溃，数据库可能还没留下预约。**我用更早的拒绝换到了吞吐，同时也必须承担更明确的故障恢复责任**，不能只看 QPS 提升，不讨论这个窗口。

- **优化目标**：售罄请求不再进入数据库事务和热点行锁竞争。
- **顺序代价**：Redis 已占用、数据库尚未提交之间出现双写窗口。
- **配套机制**：异常回滚、已入库任务恢复，以及未入库孤儿占用清理。

- [ ] **Q26：Lua 扣了库存，MySQL 插入失败怎么办？进程直接崩溃呢？**

如果只是数据库操作抛异常，当前进程还活着，就可以捕获异常，再用带预约归属校验的 Lua 释放名额。但进程直接崩溃就不同了，catch 根本没有机会执行。项目启动时会检查较老的占用，确认数据库没有对应预约后再释放。这里有个需要承认的缺口：**启动时还不满 600 秒的孤儿会被跳过，而当前没有周期扫描持续清理它**。我会优先补这条恢复链路，而不是说任务表已经覆盖所有故障。

- **普通异常**：按 reservationId 校验归属后回滚 Redis 占用。
- **进程崩溃**：无法执行 catch，需要识别 Redis 有占用、数据库无预约的孤儿。
- **当前缺口**：孤儿清理在启动时执行，并跳过不足 600 秒的占用；尚无周期清理保证。

- [ ] **Q27：Redis 重启后库存怎么恢复？为什么不能直接覆盖成 MySQL stock？**

不能简单地定时把 MySQL 库存 SET 到 Redis。比如数据库还剩 10 张，其中 2 张已经被预约预扣、但订单还没生成，Redis 的可受理余量可能是 8；这时强行覆盖成 10，就把已经占走的名额重新放出来了。项目是在键缺失时，在库存行锁保护下做初始化，再结合有效订单和持久化任务恢复占用。**即便恢复过程中 Redis 暂时不准确，最后落单仍要通过数据库条件扣减和唯一约束。**

- **重建条件**：库存键缺失时，锁数据库库存行后初始化，不随意覆盖已有值。
- **恢复内容**：数据库余量、有效订单占用，以及处理中预约的任务重放。
- **两种口径**：Redis 已预扣的请求可能还没在 MySQL 扣减，两个数字不必时时相等。

- [ ] **Q28：为什么回滚脚本必须比较 reservationId？**

假设用户第一次预约取消了，之后又成功发起第二次预约。这时第一次预约的旧补偿消息才到，如果只按“用户加票档”删占用，就会把第二次预约的票释放掉，甚至把库存多加一次。所以释放前必须比较当前记录的 reservationId，只有还是自己那次预约，才允许修改。**这跟删除缓存不一样，释放的是有主人、有生命周期的资源**；消息可以晚到，但不能让它操作别人的新状态。

- **风险来源**：旧消息和旧补偿可能比新预约更晚到达。
- **释放规则**：只释放自己这次预约持有的占用，而不是只看 userId。
- **幂等效果**：重复释放或归属不符时不再加库存，不误伤新预约。

- [ ] **Q29：票档元信息为什么只缓存 30 秒？会不会读到旧价格？**

票档元信息每次都查库也会成为入口成本，所以这里做了 30 秒缓存。它比活动介绍更敏感，因此过期时间更短，但我不会说这样就没有旧数据了：管理员刚改价，短时间内仍可能读到旧值。项目会把受理时确认的价格保存下来，后续建单按这份快照处理。**短 TTL 解决的是过期多久，交易快照解决的是同一次预约前后是否按同一条件执行**，两者不是一回事。

- **减少重复查询**：短期缓存票价、状态和售卖时间，缺失结果也有短 TTL。
- **接受的代价**：30 秒是过期上限设计，不代表管理员修改后立即可见。
- **交易快照**：受理时记录确认的价格与抵扣选择，消费阶段校验快照。

- [ ] **Q30：售罄后有候补，普通抢票请求能插队吗？**

不会把“Lua 抢到了”直接等同于最终有资格拿票。因为一张退回的票可能已经应该分给候补队首，普通预约后面还要在库存行锁保护下检查队列优先级。如果发现已有候补，就不能绕过去，前面的 Redis 预扣也要安全释放。这样候补和直接预约有一个共同的裁决点。**Redis 决定能不能先尝试，数据库事务决定这次分配是否符合业务规则。**

- **仲裁位置**：普通预约和候补推进都通过数据库库存行锁协调。
- **优先级**：有有效候补队列时，普通请求不能仅凭 Lua 预扣就绕过队列。
- **公平口径**：保障数据库队列顺序，不承诺按用户点击的绝对时间排序。

## 04｜MySQL、锁、索引与事务

- [ ] **Q31：为什么用生成列 active_flag 实现“一人一个有效订单”？**

如果直接给用户和票档建唯一索引，用户取消以后就永远不能再买了；如果把状态也放进唯一索引，又可能连多条取消历史都存不了。这里用生成列表达“是否还占资格”：有效订单是 1，取消后是 NULL，利用 MySQL 唯一索引允许多个 NULL 的特点保留历史。**约束的是同一时间不能有两张有效票，不是一个用户一辈子只能创建一条订单。**预约侧还会把释放中的记录算作有效，防止重购过早发生。

- **业务要求**：同票档不能重复持有有效订单，但取消后允许重新买。
- **约束方式**：有效订单 active_flag 为 1，取消后为 NULL，配合用户和票档组成唯一索引。
- **预约保护**：预约还要把待释放状态算作有效，避免旧补偿影响新购买。

- [ ] **Q32：哪些索引直接服务于核心交易链路？**

我会把索引分成两类讲。一类是保证规则，比如一个用户不能同时持有同票档的两个有效订单，同一个请求号也不能插入两次。另一类是服务高频查询，比如任务扫描总是在找“未完成且到了重试时间”的记录，候补要快速找到某个票档的队首。**不是给常见字段各建一个索引就够了，而是看它们怎样组合查询**。尤其有范围条件或 IN 再排序时，不能只看列顺序就断言一定没有 filesort。

- **防重复**：有效订单唯一索引、用户请求号唯一索引、任务类型唯一索引。
- **找待办**：任务状态与下次重试时间索引，候补按票档、状态和 ID 查队首。
- **设计方法**：从过滤条件、排序和约束出发，再用执行计划验证。

- [ ] **Q33：MySQL 有哪些锁？怎么结合本项目回答？**

我一般先按范围讲全局锁、表锁和 InnoDB 行级锁，再补充共享锁和排他锁是访问模式，不能混成同一张分类表。行级锁里，记录锁保护已有索引记录，间隙锁主要限制向区间插入，临键锁则把记录和间隙一起覆盖。落到这个项目，最常用的是在事务里用 FOR UPDATE 锁库存或预约，协调并发处理。**但防超卖不是“加了行锁就结束”，还要检查更新条件、影响行数和唯一约束**。锁的具体范围也要看索引、隔离级别以及记录是否存在。

- **先说明引擎和维度**：以 InnoDB 为主，锁的范围与共享、排他模式不是同一种分类。
- **范围与用途**：全局锁、表锁、行级锁；MDL 保护表结构，意向锁协调表锁与行锁。
- **行锁细分**：记录锁锁索引记录，间隙锁限制区间插入，临键锁是记录与前方间隙的组合；还有插入意向锁。
- **项目落点**：FOR UPDATE 协调库存和预约；条件更新、唯一约束共同保护最终结果。

- [ ] **Q34：SELECT … FOR UPDATE 一定只锁一行吗？没索引会升级表锁吗？**

不一定。SQL 最后返回一行，不代表执行过程中只锁一行。比如按已有主键精确查找，通常可以锁到对应记录；如果是范围查询，或者查询不存在的记录，在某些隔离级别下就可能涉及间隙。没有合适索引时，扫描和锁定的范围也会扩大，让其他请求明显受阻。但我不会把它说成“行锁自动升级成表锁”。**分析锁要看执行计划和隔离级别，而不是只看 WHERE 后面写了几个条件。**

- **执行路径决定范围**：唯一键等值命中已有记录，通常只需锁对应记录。
- **范围与不存在记录**：在 RR 等条件下可能涉及间隙锁或临键锁。
- **纠正常见误区**：无合适索引可能扫描并锁住大量记录，不等于 InnoDB 自动把行锁升级成表锁。

- [ ] **Q35：MVCC、快照读和当前读在项目里分别解决什么？**

MVCC 主要解决的是读写并发时，不必让每个普通查询都等着写事务结束。但抢票不能只靠普通 SELECT 查到的库存来决定下单：两个事务完全可能都看见还剩一张。真正分配时，要通过当前读加锁，或者带 stock 大于 0 的条件更新来裁决。**快照读适合“查看当时能看到的数据”，当前读和更新约束负责“现在能不能把这张票分给你”**。项目也没有显式改出一套特殊隔离级别来替代这些约束。

- **快照读**：普通查询通常通过 MVCC 读取可见版本，减少读写互相阻塞。
- **当前读**：FOR UPDATE、UPDATE 等需要面向当前状态并参与加锁。
- **业务区别**：看见还有库存，不等于已经获得库存；关键判断要和修改协调。

- [ ] **Q36：库存为什么用 UPDATE … stock > 0？Redis 不是已经扣过了吗？**

Redis 预扣只是让请求先拿到一个处理资格，不应该成为数据库无条件扣库存的理由。缓存可能重建，消息可能重放，系统也可能出现异常状态，所以数据库仍然要执行“库存大于 0 才减 1”。如果影响行数是 0，就说明这次没有扣到，不能继续当作成功。**最后一张票能不能真正落成订单，由数据库原子更新裁决**，而不是 Java 先查出 1，再无条件写成 0。

- **两套库存角色不同**：Redis 是准入余量，MySQL 是最终交易库存。
- **原子裁决**：更新时同时检查 stock > 0，通过影响行数判断是否扣到。
- **事务配合**：数据库扣减、订单、积分等一起提交或回滚。

- [ ] **Q37：这个项目可能死锁吗？怎么处理？**

有可能，使用了事务和行锁并不代表没有死锁。比如一条链路先锁预约再锁库存，另一条链路顺序相反，就值得重点检查。我的处理思路是先统一访问顺序，减少持锁期间的慢操作，再结合数据库的死锁信息确认是哪两条事务互相等待。发生后可以对可重放事务有限重试，但不能无限循环。**尤其有 Redis 或 MQ 副作用时，不能认为数据库回滚了，外部操作也自动撤销了**，重试必须继续满足幂等。

- **承认可能性**：涉及预约、库存和积分账户等多行操作，存在锁顺序冲突风险。
- **减少风险**：尽量统一加锁顺序、缩短事务、降低热点行等待。
- **故障处理**：检查死锁信息；对已回滚、可幂等重放的事务做有界重试。

- [ ] **Q38：如何验证索引真的有效？name AND age 有一列没索引就全失效吗？**

不会因为 age 没索引，就让 name 的索引必然失效。对于 name 等值并且 age 也满足某条件的查询，数据库可以先用 name 缩小范围，再检查 age。到底这样更快还是直接扫描更快，要看匹配的数据有多少。项目里我也会用同样方法检查任务扫描和候补队首查询：**先看执行计划和实际扫描量，再决定是否调整联合索引**，而不是看到 WHERE 有多个字段就把每个字段都建一遍索引。

- **验证工具**：看 EXPLAIN 的访问方式、实际使用索引、扫描量和排序信息。
- **AND 不是一票否决**：可以先走 name 索引，再过滤 age，优化器也可能按成本选择扫描。
- **优化依据**：结合数据分布、选择性、返回量和写入成本，而不是背固定结论。

- [ ] **Q39：@Transactional 能把 Redis 和 MQ 一起回滚吗？传播行为有什么用？**

不能。方法加了 @Transactional，并不代表它里面调用的 Redis 和 RabbitMQ 都加入了数据库事务。比如 Redis 已经扣掉库存，后面插订单失败，MySQL 可以回滚，但 Redis 要自己补偿。传播行为则是在数据库事务内部管理调用边界：MANDATORY 强调必须在已有事务里调用，REQUIRES_NEW 则另开事务。**项目把数据库先提交，再通过独立事务推进 Redis 释放**，这样补偿失败不会抹掉已经成功提交的取消记录。

- **事务范围**：这里的本地事务管理数据库，不会自动回滚 Redis 写入或已发送消息。
- **MANDATORY**：要求调用方已经有事务，避免关键操作脱离既定事务执行。
- **REQUIRES_NEW**：补偿释放使用独立新事务，失败保留任务，后续可以再试。

- [ ] **Q40：积分扣减为什么和订单放在同一个事务里？**

积分虽然不是现金，也属于用户资产。如果先扣积分，再异步赌订单能成功，失败后就要处理一笔额外退款；反过来也可能让用户享受了抵扣但没有扣余额。所以项目把积分、库存和订单放在同一个交易库，在一个事务里完成。计算时也不是直接扣用户请求的数，而是检查余额、抵扣上限和票价。**订单记录本次真正用了多少积分，后续取消按这份记录退，不按新的优惠规则重算。**

- **一致性目标**：不能扣了积分却没有订单，也不能订单享受抵扣但余额没减少。
- **并发保护**：锁积分账户，按余额、上限和票价计算实际抵扣。
- **留存依据**：订单保存实际使用积分，流水记录业务身份，取消时按原值返还。

## 05｜RabbitMQ 与持久化恢复任务

- [ ] **Q41：为什么要把“预约受理”和“创建订单”分开？**

抢票接口如果同步完成库存、积分、订单以及所有后续通知，用户等待时间会更长，高峰时也容易把线程都占住。拆开后，入口先确认请求有资格，并把预约和待办任务可靠保存，再由后台建单。这里最重要的不是“用了 MQ 就快”，而是**同步请求只承担受理责任，后续工作有明确的恢复依据**。代价也很明显：前端要展示处理中，后端必须解释消息失败、重复和超时以后怎么办。

- **缩短同步等待**：入口先完成必要校验和可靠受理，建单再异步推进。
- **承受流量波动**：消费者按处理能力推进，不让所有工作挤在 HTTP 请求里。
- **新增复杂度**：需要处理中状态、结果查询、重试、幂等和补偿。

- [ ] **Q42：为什么要这么多队列？分别解决什么问题？**

这些队列是按失败和时间语义分开的，不是为了数量多。正常创建消息进入建单队列，多次处理失败后进入创建死信链路。未支付订单则走另一条延迟链路，等待到期再触发取消。如果连补偿也反复失败，就进入补偿失败队列，留给排查和对账。**创建失败和支付超时是两种不同事件**，处理前提不一样，不能拿到一条异常消息就统一退库存。

- **创建链路**：建单队列处理业务，创建死信队列处理多次失败。
- **到期链路**：延迟队列通过 TTL 和死信路由，把未支付订单交给取消处理。
- **异常留存**：补偿失败队列保留难以自动处理的消息，不能等同于已经修复。

- [ ] **Q43：生产者怎么知道消息发成功了？Confirm 和 Return 有何区别？**

我会分三个层次看成功：消息是否被 Broker 接收，是否路由到了目标队列，以及订单是否真的创建。Confirm 主要回答第一层，Return 用来发现路由不到队列的情况，消费者处理完成又是另一层。项目会根据回调处理发送失败，也有短期重试，但不会因为收到 Confirm 就认为预约结束。**只要订单还没落地，数据库里的恢复任务就仍然有价值**，它能覆盖进程重启或消息后续处理失败的情况。

- **Confirm**：关注 Broker 是否确认发布，不表示消费者已完成建单。
- **Return**：mandatory 模式下识别消息没有路由到队列的情况。
- **业务完成依据**：订单落库和预约状态变化；确认发送后不能立即关闭恢复任务。

- [ ] **Q44：预约任务表算不算 Outbox？和事务消息有什么区别？**

我更愿意说它采用了类似 Outbox 的本地任务表思路。受理预约时，把“已经受理”以及“后面还要发创建消息”一起存进数据库；只要事务提交，这件事就不会只存在内存里。取消时也能用同样方式记录待释放动作。不过，它不是让 MySQL 和 RabbitMQ 同时提交的分布式事务。**任务可能被执行多次，所以可靠性靠“不会忘记要做什么”，正确性还要靠“重复做也不会多扣一次”。**

- **共同思想**：业务记录和待执行动作同库同事务，提交后再可靠推进。
- **项目形态**：任务既负责 SEND_ORDER，也负责 RELEASE，不只是存消息原文。
- **不夸大保证**：不是数据库与 MQ 的原子提交，需要重试和消费幂等。

- [ ] **Q45：多个实例同时扫描任务，会不会重复执行？claim 为什么不是 Exactly Once？**

多个实例会同时看到待办任务，所以不能先查出来，再各自认为自己拿到了。这里通过条件更新认领，成功的一方再处理，并把下一次可重试时间推后。但如果这次处理很慢，或者消息发出后进程崩溃，后面仍可能再次执行。**claim 是降低重复并提供恢复机会，不是证明这件事只会执行一次**。系统按至少一次推进来设计，让重复发送和重复消费最终都收敛到同一个业务结果。

- **抢占方式**：通过条件更新认领到期任务，并把下次重试时间向后推。
- **时间窗口**：约 30 秒的重试窗口不等于永久独占，慢处理和故障可能导致再次执行。
- **最终保证**：预约行锁、状态校验和幂等操作允许安全重放。

- [ ] **Q46：项目用手动 ACK 还是自动 ACK？消费者抛异常后发生什么？**

这个项目用的是 Spring 的 AUTO 确认模式，不是手动在业务代码里调用 ACK。正常情况下监听方法成功返回，容器才确认；抛异常则交给重试和恢复配置处理。这里有本地有限重试，持续失败后不一直重新塞回原队列，而是进入死信链路。**要特别区分 Spring AUTO 和 RabbitMQ 无确认投递，它们不是一个意思**。否则面试官继续问“业务失败了消息会不会已经没了”，就很容易解释错。

- **当前模式**：Spring AMQP 的 AUTO，由容器根据监听方法执行结果确认。
- **概念区分**：AUTO 不是 Broker 投递即忘的无确认模式，也不是业务手写 basicAck。
- **失败路线**：本地有限重试，仍失败则拒绝且不重新入原队列，进入死信处理。

- [ ] **Q47：一条创建订单消息重复消费十次，为什么不会重复扣库存？**

重复消费是正常需要处理的情况，比如订单已经提交，但消费者还没来得及确认就断开了。第二次消息进来时，不能重新走一遍无条件扣库存，而要锁定预约、检查状态和订单是否存在。订单已经创建就按已有结果收敛，只有真正的新建流程才扣库存、扣积分并插入订单。**锁负责减少同时执行的冲突，状态和唯一约束负责阻止重复副作用**，所以即使消息来了十次，也不应该扣十次。

- **减少竞争**：用户维度 Redisson 锁协调同用户消费。
- **数据库判断**：锁预约，核验状态和消息快照，检查目标订单是否已经存在。
- **最终约束**：订单唯一性与事务保证，不把分布式锁当作唯一防线。

- [ ] **Q48：消息进死信队列就直接返库存，为什么危险？**

最典型的反例是订单已经写进数据库，消费者在 ACK 前出了问题，消息后来进入死信。如果这时直接把库存加回去，就会出现订单还有效、票却又被卖出去的情况。所以死信处理先看数据库事实：订单到底有没有创建，预约现在是什么状态。**死信说明某次消息处理不顺利，不代表业务一定失败**。先做状态裁决，再决定要不要补偿，比简单地“异常就回滚库存”重要得多。

- **死信不等于没建单**：事务可能已经提交，只是确认或后续步骤失败。
- **先查事实**：检查订单是否存在，再锁预约判断能否终止建单。
- **补偿前提**：只有明确进入失败状态的预约，才安排归属安全的释放。

- [ ] **Q49：按崩溃位置梳理：每一步失败由谁恢复？**

我会沿着链路分段解释。预约还没入库就崩溃，任务表帮不上忙，要检查 Redis 孤儿占用；预约和任务已经提交，但消息没发出去，扫描任务会继续推进；订单已经提交，只是消息没确认，重复消费要识别已有订单。取消也是一样，数据库已取消但 Redis 没释放，就保留 RELEASE 任务重试。**恢复机制必须对应具体断点，不能只说“我们有 MQ 重试，所以不会丢”**。其中入库前的孤儿清理，是目前最应该补强的地方。

- **入库前**：Lua 成功但预约未提交，依靠异常回滚或孤儿检查，当前仍有清理缺口。
- **入库后**：任务扫描补发消息；建单后重投由订单幂等处理。
- **取消后**：RELEASE 任务修复 Redis 释放；丢失超时消息由订单扫描兜底。

- [ ] **Q50：消息进入补偿失败队列后，系统会自动修复吗？**

目前不能说会自动修好。补偿失败队列的价值是把问题留下来，避免消息悄悄消失，但留下来不等于处理完了。后续应该先看对应订单是否存在、预约有没有结束、Redis 现在由谁占用，再选择安全重放或人工修复。**不能为了清空队列就批量执行返库存**，因为一些消息的业务可能早已成功。这部分如果用于生产，我会补告警和带审计记录的处理入口。

- **当前能力**：失败消息被保留下来，但没有对应的自动修复消费者。
- **处理顺序**：先核对预约、订单、库存和归属，再决定重放还是人工修正。
- **下一步建设**：告警、可审计的重放工具和对账机制，避免盲目重复补偿。

## 06｜订单状态、积分、签到与候补

- [ ] **Q51：预约成功和订单已支付有什么区别？状态为什么要分开？**

预约成功的意思是订单已经创建，不是用户已经付钱。比如用户抢到票以后，预约可以是成功，但订单还在待支付；支付后订单变成已出票，预约不需要再变一个“已支付”状态。取消以后，还可能有一个资源释放中的阶段，用 release_pending 单独记录。**这三件事分别是处理进度、交易状态和补偿进度**。分开以后，前端展示和后台重试才不会拿一个“成功”解释所有情况。

- **预约状态**：处理中、成功、失败、取消，描述一次受理流程。
- **订单状态**：待支付、已出票、已取消，描述交易结果。
- **补偿标记**：release_pending 描述资源释放进度，不是支付状态。

- [ ] **Q52：支付和超时取消同时发生，谁赢？**

不是看哪个 HTTP 请求先到，也不是前端倒计时归零就算最终结果。支付 SQL 要求订单属于当前用户、仍待支付，而且没超过数据库判断的截止时间；到期取消则检查相反的时间条件。两个操作落到同一行，由数据库加锁和条件检查决定谁能成功。**即使扫描器还没来得及取消，已经过期的订单也不能继续支付**。当前这里是模拟支付，真实渠道回调和退款还需要额外设计。

- **数据库裁决**：支付和取消都用条件更新，不先查完再无条件修改。
- **时间互补**：支付要求未到截止时间；到期取消要求已到截止时间，统一使用数据库时间。
- **副作用只做一次**：只有真正把待支付改为已取消的一次操作，才能返库存和积分。

- [ ] **Q53：为什么既有 15 分钟延迟消息，又有数据库扫描？**

延迟消息适合正常情况下把到期订单叫醒，但如果发送失败、MQ 不可用或者消费积压，只靠它就可能长期占票。所以数据库还会定时扫描已经到期的未支付订单。两条路径最后都调用带状态和时间条件的取消逻辑，重复触发也不会重复退款。**延迟消息负责及时性，数据库扫描补恢复能力**。不过每批只有固定处理量，严重积压时不能承诺所有订单恰好在第 15 分钟完成释放。

- **正常推进**：延迟队列到期后触发取消，减少频繁全量检查。
- **兜底恢复**：每 60 秒扫描最多 500 条到期未支付订单，逐笔处理。
- **不承诺精确触发**：消息可能延迟，数据库条件防止提前取消，积压会影响回收速度。

- [ ] **Q54：一次取消涉及数据库、Redis 和积分，怎么保证不重复补偿？**

取消不是收到请求就把库存加 1。先看这次能不能把订单从待支付改成已取消，更新失败就说明不能继续返还。真正取消成功时，数据库库存、积分和待释放任务一起提交，再去处理 Redis。如果 Redis 暂时不可用，订单仍然保持取消，后续根据任务重试释放。**数据库靠状态转换避免重复返还，Redis 靠预约归属避免重复或错位释放**。这套完整保证主要针对新的预约链路，兼容旧订单的分支不能一概而论。

- **先赢得状态变更**：订单由待支付改为取消成功，才能执行返还。
- **数据库一起提交**：库存、积分、预约状态和 RELEASE 任务保持本地事务一致。
- **Redis 后续释放**：新事务校验预约归属并释放，失败留任务重试；旧订单兼容路径保证较弱。

- [ ] **Q55：订单已经取消，为什么用户可能还不能马上重新预约？**

这通常不是订单还没取消，而是后台正在释放这次预约占用的资源。比如取消时 Redis 故障，数据库可以先完成取消和积分返还，但如果马上允许新预约进来，旧补偿之后就可能和新占用发生冲突。所以项目会暂时保留这个用户对该票档的有效资格，等安全释放后再放开。**这里选择的是短暂等待，而不是冒险让新旧预约互相覆盖**。界面也应该解释成“取消成功，资源释放中”，不能只给用户一个模糊失败。

- **中间状态**：数据库取消完成，不等于 Redis 的旧占用已经释放。
- **安全约束**：release_pending 为 true 时仍占有效预约资格。
- **恢复条件**：释放任务完成后清标记，才允许用新请求发起购买。

- [ ] **Q56：怎么防止积分超扣、重复退款或者按新规则退错？**

我会把它当成一笔资产变动来处理，而不是随手改一个积分字段。扣减时先锁账户，算出这张订单实际能用多少，再把余额、流水和订单一起提交。取消时读取订单原来用了多少，只退这个数。比如下单用了 300 积分，后来活动优惠变了，也不能按新规则退 500。**状态控制决定该不该退，订单快照决定退多少，流水负责留证和防重**，三者需要配合。

- **防超扣**：锁账户，检查余额和抵扣限制，余额更新与流水同事务。
- **防重复**：订单首次取消成功才返还，流水还有业务唯一约束。
- **按原值返还**：使用订单保存的实际抵扣积分，不按当前价格或规则重新计算。

- [ ] **Q57：签到如何做到一天只发一次积分？为什么先落数据库再 SETBIT？**

签到最重要的是不能重复发积分。项目先在数据库里确认当天是否已经有签到流水，没有才发 10 积分，并把余额和流水一起提交，然后再更新 Redis 位图。这样即使位图更新失败，用户重试时也能从流水知道奖励已经发过，只补签到标记。**我优先保证资产正确，再修复展示状态**。它不是数据库和 Redis 强一致；如果用户不重试，当前也没有一个通用后台任务把所有丢失的签到位图都自动补全。

- **并发控制**：用户与日期维度锁，加上账户行锁和签到流水唯一约束。
- **提交顺序**：先提交 10 积分奖励与流水，再设置签到位图。
- **重试修复**：已有当天流水就不重复发奖，只补 Redis 标记。

- [ ] **Q58：Bitmap 怎么算连续签到？为什么原始字节比逐日查询更合适？**

一个月最多 31 天，用 31 个 bit 就能表示这个月哪天签到了。查询连续天数时，如果一天发一个 Redis 请求，网络往返会比位运算本身贵得多，所以现在按月拿原始字节，在内存里判断和计数，同一个月只读一次。实现上要注意 Redis 位偏移从字节高位开始，Java 的 byte 也有符号，计数时需要按无符号值处理。**省的是反复访问 Redis 的成本**；跨月仍可能多读一个月，4 字节也只是位数据，不是整个键的内存。

- **存储方式**：每用户每月一个 Bitmap，日期减 1 是位偏移；31 位载荷约 4 字节。
- **读取优化**：一次请求内按月读取并复用 byte[]，在本地统计，不逐天往返 Redis。
- **细节**：按高位到低位取 bit，处理 byte 的符号；跨月读取上月，今天未签到可从昨天回溯。

- [ ] **Q59：候补为什么用 MySQL 队列，而不是 Redis ZSet？**

Redis ZSet 可以做排序，但这个项目的候补不是只排个名次，还要跟库存、预约生成和失败恢复一起处理。把它放在 MySQL 里，可以用同一个事务检查队首、锁库存、生成预约并记录任务，状态更容易协调。队列顺序按自增 ID 判断。**我选择数据库不是因为 Redis 做不了队列，而是这条业务更需要事务和可恢复的状态**。如果以后排队规模明显扩大，再结合瓶颈评估是否引入更专门的队列方案。

- **实际结构**：数据库候补表，自增 ID 表示排队顺序。
- **一致性方便**：候补、库存仲裁、预约和任务可以放进同库事务。
- **公平边界**：按数据库队列序号推进，不承诺按用户点击的绝对时间排序。

- [ ] **Q60：候补分配失败会不会丢位置？分配成功后取消呢？**

如果是系统分配过程失败，用户不应该因为这次失败被扔到队尾。项目会等预约失败后的资源释放完成，再把候补改回等待状态，保留原来的队列 ID。但用户已经分配成功，后来自己取消订单，就不是同一回事，不会自动恢复原位置。**系统失败保留公平性，用户完成分配后的主动取消按新的业务行为处理**。这种设计也会产生队首阻塞，所以要关注分配中状态停留了多久。

- **队首推进**：等待中转为分配中，生成预约和任务；处理中不让后续越过。
- **失败保位**：确认预约失败且资源释放完成，再回到等待，保留原队列 ID。
- **成功后取消**：已经分配成功的用户取消订单，不自动回到原来的候补位置。

## 07｜Redis、缓存与故障边界

- [ ] **Q61：Redis 在项目中存了哪些数据？为什么选这些结构？**

我不会为了用全 Redis 数据结构而设计功能，而是按操作需求选。库存需要原子减，所以用数值 String；预约要根据用户找到归属，用 Hash；判定用户是否已经占票，用 Set。点赞和 Feed 需要按时间排序，适合 ZSet，签到只记录有或没有，适合 Bitmap。**同样都是缓存数据，访问方式不同，结构也应该不同**。尤其不要把候补说成 ZSet 队列，这个项目的候补用的是数据库表。

- **String、Hash、Set**：分别承载余量或缓存对象、会话或归属字段、占用用户判重。
- **ZSet**：点赞与 Feed 按时间排序；候补实际存在 MySQL，不要串项目。
- **专门能力**：Bitmap 表示签到，GEO 查询附近活动，HyperLogLog 估算 UV。

- [ ] **Q62：项目怎么防缓存穿透？缓存命中返回什么？**

如果一个不存在的活动每次都查数据库，缓存就帮不上忙了。所以项目对查不到的结果也缓存一个短期空值标记，同一个 ID 再来时直接返回不存在。正常存在的数据则缓存详情对象，命中后不用重复组装。**空值缓存解决的是同一个无效请求反复穿透**；攻击者不断换随机 ID 时，仍需要参数校验、请求限制等配合。空值也不能缓存太久，否则新建资源可能短时间内还被认为不存在。

- **正常命中**：活动详情缓存完整展示对象，命中后反序列化返回。
- **空值缓存**：查不到的数据保存短期空值标记，约 2 分钟内不反复回源。
- **能力边界**：能挡重复访问同一个不存在 ID，不能独自挡住海量随机 ID。

- [ ] **Q63：缓存击穿、雪崩分别怎么解决？哪些是项目已经做的？**

我会先分清问题：一个热门活动的缓存突然过期，大量请求同时查库，是击穿；很多键一起过期或者 Redis 整体出问题，导致大面积回源，是雪崩。前者更适合控制同一个键的重建，后者更需要削减整体回源压力。**这些是可以采用的方案，不是项目已经全部实现的能力**。当前主要有详情缓存和短期空值缓存，如果继续优化，我会先针对真正的热点增加请求合并或受控重建。

- **击穿**：单个热点键失效，考虑请求合并、互斥重建或逻辑过期。
- **雪崩**：大量键同时失效或 Redis 故障，考虑 TTL 打散、限流和分级降级。
- **项目事实**：已有详情缓存和空值缓存，没有通用的逻辑过期或互斥重建框架。

- [ ] **Q64：为什么更新数据库后删除缓存？这样就绝对一致了吗？**

删除缓存比直接更新整个缓存对象更容易维护，尤其一个详情对象还包含分类等组合信息时。但先改数据库再删缓存也不是强一致：删除可能失败，慢查询也可能在删除之后把旧值写回。这个项目采用的是常见的 Cache-Aside 思路，允许一定程度的短期旧数据。**如果业务要求更严格，需要把失效动作变得可重试，或者引入版本判断等方案**，不能因为写了“延迟双删”四个字就认为所有竞争都消失了。

- **当前策略**：更新活动数据，再删除相关缓存，下次读取时重建。
- **仍有窗口**：删缓存失败，或并发读取将旧值重新写回，都可能留下旧数据。
- **改进选择**：根据容忍度使用短 TTL、可靠失效任务、版本控制或 CDC。

- [ ] **Q65：Redis 挂了，整个项目能不能自动降级到 MySQL？**

不能笼统地说能。活动详情可能有讨论回源的空间，但登录态就在 Redis，预约和 ID 生成也依赖它，Redis 故障会直接影响这些请求。数据库里已经提交的预约和任务还在，恢复后可以继续推进，并不等于故障期间所有接口都能正常服务。**我会逐条链路区分“能恢复数据”和“还能实时提供服务”**。即使给详情加回源，也要限制流量，否则只是把 Redis 故障变成数据库被打垮。

- **不只是缓存**：会话、预约预扣、ID 序列和分布式锁也依赖 Redis。
- **当前事实**：没有覆盖所有接口的自动回源降级能力。
- **分级设计**：展示数据可评估受限回源，身份和交易不能无条件放行。

- [ ] **Q66：AOF、主从和 Cluster 能保证 Redis 库存绝不丢吗？**

不能。AOF 能提高可恢复性，但是否丢最近写入还取决于刷盘策略和故障场景；主从复制也不代表任何时刻都完全同步。这个项目当前还是单节点 Redis，只是在多键命名时让同一票档落在同一个 hash slot，便于未来使用 Cluster。**这种准备不等于已经有 Redis 集群，更不等于一个热点票档能被无限拆开处理**。最终订单的库存正确性仍由 MySQL 条件更新和约束守住。

- **当前部署**：单节点 Redis 开启 AOF，没有部署 Sentinel 或 Cluster。
- **数据风险**：持久化与复制都有具体故障窗口，不能承诺绝对零丢失。
- **多键脚本**：同票档使用相同 hash tag，适配同槽执行，但不会自动分散单个热点。

- [ ] **Q67：Redisson 看门狗能保证业务永远持锁吗？**

看门狗解决的是业务执行时间不固定时，不用随便猜一个锁过期时间。但它要依赖客户端及时续期，如果发生很长的 GC 停顿或者网络分区，锁仍可能到期，被另一个执行者拿走。旧线程恢复后，不能因为自己之前拿过锁，就继续认为一直独占。**所以我把分布式锁当成协调手段，不当成数据库约束的替代品**。更严格的旧持有者隔离可以讨论 fencing token，但当前项目没有完整实现这套机制。

- **正常机制**：未指定固定租期时，客户端通过看门狗自动续期。
- **异常边界**：长 GC、网络中断、Redis 故障可能导致续期失败。
- **业务保护**：只释放当前线程持有的锁，最终写入仍依赖数据库状态和约束。

- [ ] **Q68：项目订单 ID 是雪花算法吗？时间回拨会怎样？**

它不是标准雪花算法。项目把相对时间放在高位，把 Redis 自增序列放在低位，通过共享序列协调多个实例，所以不需要每个实例分配机器号。代价是生成 ID 依赖 Redis。时间回拨也不能直接套用雪花算法的结论，要结合当天的序列是否仍然单调、计数器有没有丢失来分析。**我能说明当前编号怎么组成，但不会说它已经覆盖所有时钟异常和容灾切换场景**。生成后传给前端还要处理 Long 精度。

- **实际结构**：相对秒时间戳左移 32 位，再组合 Redis 自增序列，不是标准 Snowflake。
- **唯一性依赖**：多实例共享按日期递增的序列，没有独立机器号字段。
- **异常评估**：考虑时钟异常、计数器重置和容量边界，不夸大未验证的容灾能力。

- [ ] **Q69：附近演出与 UV 分别怎么做？为什么 UV 不能当精确人数？**

附近活动先利用 Redis GEO 找出距离符合条件的活动 ID，再批量查详情，最后按原来的距离顺序组装，不能让 SQL IN 的返回顺序打乱结果。UV 用 HyperLogLog 是因为只需要低成本估算独立访问量，不需要保存每个访问者。**它既有算法上的近似误差，也有身份识别的口径问题**：同一个 IP 可能有多人，同一个人也可能换网络或先匿名再登录，所以不能把这个数字当成精确用户数。

- **附近活动**：GEO 按距离取 ID，数据库批量补详情后恢复距离顺序。
- **UV**：HyperLogLog 近似去重，使用用户或匿名 IP 标识。
- **统计边界**：近似算法与身份口径都会产生偏差，不等于真实到场或付费人数。

- [ ] **Q70：Pipeline、Lua、事务各有什么区别？项目里什么时候用？**

我会按要解决的问题选。批量查询一页评价的点赞状态，主要想少跑几趟网络，可以用 Pipeline；库存要先判断再扣减，中间不能被其他请求插入，就用 Lua。订单、库存和积分要一起提交或回滚，则靠 MySQL 本地事务。**减少网络往返、保证 Redis 操作原子性、保证交易数据一致性，是三种不同目标**。Pipeline 再快也不能替代库存脚本，Redis 的事务也不是带数据库回滚能力的跨系统事务。

- **Pipeline**：批量发送命令减少网络往返，不保证多命令整体原子性。
- **Lua**：在 Redis 内执行带条件的原子逻辑，适合库存预扣与归属释放。
- **事务范围**：Redis MULTI/EXEC 与 MySQL 事务语义不同，都不能自动覆盖另一套系统。

## 08｜Java 并发、Spring 与互动链路

- [ ] **Q71：任务线程池为什么用 4 个线程、1000 长度队列？满了会怎样？**

这个线程池不是唯一保存任务的地方，它只是让事务提交后的任务尽快执行。真正的待办已经在数据库里，所以队列满了，被丢掉的是这次立即执行的机会，不是业务任务本身，后面扫描还会处理。**如果没有持久化任务表，静默丢弃在这里就很危险**。4 个线程和 1000 队列也不是通用最优值，需要看任务耗时、积压和下游承载能力；继续完善时，我会优先把拒绝次数和最老任务等待时间监控起来。

- **当前配置**：核心与最大线程数都是 4，有界队列 1000，拒绝策略为 DiscardPolicy。
- **安全前提**：线程池只加速已持久化任务，被丢弃的提交仍可通过数据库扫描恢复。
- **配置取舍**：限制并发与内存占用，但具体容量需要结合数据库和 MQ 的处理能力验证。

- [ ] **Q72：为什么使用 ObjectProvider？它解决了什么问题？**

这里存在一个相互调用的关系：预约受理后要触发任务，任务执行时又要调用预约服务。如果双方都急着在构造阶段拿到对方，就容易形成初始化依赖问题。ObjectProvider 相当于先保留一个获取入口，等真正处理任务时再取 Bean。**它解决的是对象什么时候获取，不是让业务依赖凭空消失**。如果后面相互调用越来越复杂，我会考虑抽出更清晰的编排层，而不是到处加延迟注入掩盖设计问题。

- **依赖关系**：预约服务需要调度任务，任务处理器又需要调用预约服务。
- **延迟获取**：通过 ObjectProvider 在实际调用时取得 Bean，缓解初始化依赖环。
- **设计边界**：延迟注入不等于业务解耦，调用职责仍要保持清晰。

- [ ] **Q73：Spring 事务为什么会失效？自调用、异步和提交后回调要注意什么？**

我会先看这次调用到底有没有经过 Spring 代理。比如同一个类里直接调用另一个标了事务的方法，不等于开启了它声明的新事务；把任务扔进线程池，也不会把原来的事务一起带过去。项目在一些调度和编排场景里用 TransactionTemplate 明确事务范围，取消后的释放则通过代理开启新事务。**事务注解不是贴在方法上的永久属性，是否生效取决于调用方式和执行线程**。提交后回调里也不能默认还有一个能继续提交的原事务。

- **代理边界**：同类内部直接调用不经过事务代理，不能指望被调用方法的注解重新生效。
- **线程边界**：新线程不会自动继承调用方的数据库事务。
- **项目做法**：需要明确边界时使用 TransactionTemplate，提交后释放通过代理开启新事务。

- [ ] **Q74：synchronized、volatile、CAS 能替代分布式锁或数据库约束吗？**

不能直接替代。单机测试里，在下单方法上加 synchronized 可能看起来没有超卖，但部署两个实例以后，每个 JVM 都有自己的锁，彼此不会互斥。volatile 也只能解决特定可见性和有序性问题，不能把“检查库存再扣减”自动变成原子业务。CAS 适合某些共享内存状态竞争，也不是跨数据库和服务的事务。**要先问状态到底共享在哪里，再选择在那个层面生效的同步手段。**

- **synchronized**：协调同一 JVM 内访问同一监视器的线程。
- **volatile / CAS**：分别侧重可见性与单次条件更新，不自动覆盖复合业务和多实例。
- **跨实例裁决**：依靠 Redis 原子操作、数据库锁和唯一约束等共享协调点。

- [ ] **Q75：异步任务和 MQ 消费能直接使用请求线程的 UserHolder 吗？**

不能。请求结束时，原线程上的用户信息就应该被清理了，后面的消息消费可能发生在另一台机器，更不可能继续读取那份 ThreadLocal。这里需要把 userId、预约号、订单号等必要信息放进持久记录和消息，再在消费时核验它们是否匹配。**身份要随着业务数据明确传递，而不是靠某个线程“记得刚才是谁”**。这也能避免线程池复用时，错误继承前一个任务的用户上下文。

- **线程不同**：HTTP 请求、线程池和 MQ 消费一般不是同一个线程。
- **显式传递**：任务和消息携带必要业务身份，并与预约记录核验。
- **防止泄漏**：不把普通 ThreadLocal 当成自动上下文传播机制。

- [ ] **Q76：项目如何避免 N+1 查询？批量查询后为什么还要重新排序？**

比如一页有 20 条评价，如果每条都单独查作者，就会从一次列表查询变成很多次数据库访问。现在先收集作者 ID，批量查回来放进 Map，再组装结果；点赞状态也尽量批量访问 Redis。还有一个容易遗漏的点：GEO 或 Feed 已经排好了顺序，但数据库用 IN 查详情不会保证沿用这个顺序。**批量查询解决次数，按原 ID 列表组装解决顺序**，两个步骤缺一不可。

- **数据库批量化**：先收集用户等关联 ID，一次查询后用 Map 组装。
- **Redis 批量化**：一页评价的点赞状态用 Pipeline 减少网络往返。
- **顺序恢复**：SQL IN 不保证按传入 ID 顺序返回，Feed 和 GEO 结果需按原顺序还原。

- [ ] **Q77：点赞用 ZSet 后，能保证点赞状态和计数强一致吗？**

ZSet 能方便判断用户是否点过赞，也能按时间列出最近点赞的人。项目不会只根据先查到的状态去盲目加减计数，而是看这次 Redis 操作到底有没有真的添加或删除。但它仍然是 Redis 和数据库两步操作，中间失败或者并发交错时，计数与状态可能不一致。**减少重复计数，不等于实现了跨系统强一致**。如果继续完善，我会考虑明确“设为点赞或取消”的接口语义，并补充可恢复的事件或对账方案。

- **结构作用**：ZSet 记录点赞用户和时间，可查询最近点赞者。
- **当前改进**：根据 ZADD、ZREM 的真实返回结果决定是否修改数据库计数。
- **剩余风险**：Redis 与数据库不是同一个事务；toggle 接口也不等于幂等的“设置为已点赞”。

- [ ] **Q78：关注 Feed 为什么用写扩散？大 V 用户会有什么问题？**

当前做法是作者发评价后，把这条内容放到粉丝各自的 Feed 里，用户读取时就比较简单；新关注一个人，也会回填一部分最近内容。这个方案适合规模不大的关注关系，但大 V 发一条就可能要写很多份，发布成本会放大。**它是把工作提前到写入端，不是消除了工作量**。项目的 Feed 推送还没有像订单那样的持久化任务恢复，如果继续做大，可以考虑普通作者写扩散、大 V 读时拉取的混合方式。

- **当前方式**：评价提交后推送到粉丝的 ZSet，关注时回填最近 20 条评价。
- **读写取舍**：用户读 Feed 更直接，但作者粉丝越多，发布时写入越多。
- **恢复边界**：当前推送失败主要记录日志，没有持久化投递任务兜底。

- [ ] **Q79：Feed 为什么用时间游标加 offset？同一毫秒多条数据有什么风险？**

只按时间翻页有个问题：同一毫秒可能产生多条评价，所以还要记录在边界时间上已经读了多少条。比如 6 条内容时间都相同，每页 2 条，第一页读 A、B，第二页跳过 2 条读 C、D，第三页就应该跳过 4 条。如果 offset 每次只记本页的 2 条，就又会读到 C、D。**当前实现存在这种累计偏移的静态风险**，我会用这个最小场景补测试，再考虑修正累计逻辑或采用更稳定的复合游标。

- **游标设计**：max 限制时间范围，offset 跳过边界时间上已经读过的条目。
- **同分处理**：下一页仍停留在同一个时间戳时，offset 需要累计，而不是重新从本页计数。
- **当前风险**：静态分析发现同分条目跨多页可能重复，应补回归测试；不把修复建议说成已修复。

- [ ] **Q80：接口变慢时，怎么判断是不是 JVM 或 GC 的问题？**

我不会看到接口慢就先加堆内存或换垃圾收集器。如果 CPU 不高但线程都卡在数据库连接或行锁上，问题可能根本不在 GC。需要把延迟波动和 GC 暂停、线程栈、连接池等待放在同一时间段看。对于这个项目，还要注意长暂停可能让分布式锁续期不及时。**先证明时间花在哪里，再决定优化哪一层**。目前有明确证据的是热点路径和 Redis 往返优化，不应该额外包装成做过系统性的 JVM 压测调优。

- **先定位层次**：分清 CPU、线程等待、数据库锁、外部调用和 GC 暂停。
- **结合证据**：查看延迟分布、线程栈、GC 日志、堆占用和连接池状态。
- **联系业务**：长暂停还可能影响 Redisson 续期，但没有证据就不声称做过 GC 调优。

我会把测试内容和执行记录分开说。项目不只有普通方法测试，还覆盖预约失败恢复、重复消息、库存并发、候补和支付截止时间等场景，很多用 Testcontainers 连接真实中间件。前端则测试轮询、请求号保存和状态展示。**有测试代码，和这些测试在当前环境全部跑过，是两件事**。已有执行记录确认前端 17 项通过；后端测试依赖 Docker 环境，整理期间没有全量重跑，所以不能把有测试代码说成全部验证成功。

- **验证口径**：已有记录确认前端 17 项测试通过；后端与压测没有在整理期间全量重跑。

- [ ] **Q82：怎么证明没有超卖？只看接口错误率够吗？**

不够。接口都返回 200，照样可能多建了订单；压测有售罄响应，也不代表系统有异常。比如准备 50 张票，我会检查最终有效订单是否符合上限，库存是否非负，有没有同一用户重复占票，再看待处理和待释放任务是否收敛。**Redis 在受理时先扣，MySQL 在建单时再扣，中间数字不相等不一定是错误**。真正要证明的是：并发和重试结束以后，订单、库存以及占用关系能够对上。

- **业务不变量**：有效订单不超过可售数量，同用户同票档没有重复有效订单。
- **完整对账**：结合数据库库存、预约任务、Redis 余量与归属检查。
- **时点区别**：处理中 Redis 预扣和 MySQL 已建单数量可能不同，要在任务收敛后核对最终状态。

- [ ] **Q83：故障恢复怎么测？模拟异常等于真实进程崩溃吗？**

恢复测试要挑断点，不是只测一个正常下单。我会让任务插入失败，看 Lua 占用是否回滚；让发送失败，看持久任务能否继续推进；让旧消息晚到，看它会不会影响新预约。项目也有重新执行初始化逻辑的测试。不过，**这类受控测试证明的是代码分支，不是完整验证了操作系统进程崩溃和中间件容灾**。真实故障演练还需要单独做，而且要在隔离环境里验证，不能拿模拟异常替代所有故障证据。

- **可控注入**：模拟任务保存失败、消息发送失败、Redis 释放失败和旧消息重放。
- **断点验证**：检查副作用、数据库状态以及后续重试是否符合预期。
- **测试边界**：调用初始化器或抛异常，不等于真的 kill 进程、断网或验证磁盘恢复。

- [ ] **Q84：支付、重复取消和超时竞争，最重要的测试用例是什么？**

我最关心的不是分别点一次支付和取消能不能成功，而是它们撞在一起会怎样。比如订单刚过截止时间，扫描器还没执行，这时支付也必须失败；用户点取消的同时，延迟消息和扫描器又各处理一次，库存和积分仍只能退一次。测试要检查最终状态和余额，而不是只断言某个方法返回成功。**时间边界、竞争结果和副作用次数，是状态机测试的三个重点。**

- **截止时间**：到期但扫描尚未取消，支付也必须被拒绝。
- **并发竞争**：支付与到期取消交错，最终只能留下合法状态和对应副作用。
- **重复补偿**：用户取消、延迟消息与扫描重复触发，不得重复返库存或积分。

- [ ] **Q85：抢票压测的“零错误”是什么意思？为什么 1000 次请求只产生 50 单也正常？**

如果总共只有 50 张票，发 1000 次请求，当然不应该产生 1000 个有效订单。合理结果可能是 50 次受理，其余按预期被业务拒绝，所以压测工具的零错误，可能只是所有响应都满足事先定义的断言。这个项目很多业务结果还通过响应体里的 code 表达，不能只看 HTTP 200。**我会分别报告入口吞吐、正常拒绝、真正受理以及最终建单数**，否则一个很高的 QPS 很容易被误解成实际卖票能力。

- **负载条件**：例如 100 线程各发 10 次请求，而票量只有 50。
- **业务断言**：成功受理、售罄和重复等预期结果要分类，不能只检查 HTTP 状态。
- **口径区分**：错误率、受理率、建单率和最终正确性不是同一个指标。

- [ ] **Q86：预约吞吐从约 223 到 728 QPS，关键优化是什么？**

最容易解释的改动，是把售罄判断提前了。票已经卖完时，请求如果还要进入事务、等库存锁、再查出没票，就是在做没有业务价值的工作。Lua 前移以后，这部分请求可以更早结束，因此入口吞吐提升明显。**这组提升很大程度上反映了拒绝路径变轻，不是数据库每秒能多创建同样比例的订单**。元信息缓存也减少了查询，但没有独立对照实验，我不会说其中某个精确百分比一定由它带来。

- **主要思路**：Lua 提前到数据库事务之前，售罄请求不再争抢库存行锁。
- **减少无效工作**：热点元信息短期缓存，降低入口重复查询成本。
- **因果边界**：多项修改和本地环境波动共同存在，没有单因素实验就不精确分摊每项收益。

- [ ] **Q87：活动详情为什么能从约 1376 提到 2511–3584 QPS？**

关键不是把一个 Redis 命令换成更快的命令，而是让缓存命中路径真正不再做多余的远程工作。活动介绍和分类信息命中后直接返回，动态票档和 UV 走独立流程，详情接口就轻了很多。历史稳态测得大约 2511 到 3584 QPS，相比原先约 1376 有提升，但不同轮次差异也很明显。**拆接口可能把一部分工作移到了别的请求，所以还要看整页体验，不能只拿单个接口数字宣布整体性能翻倍。**

- **原先成本**：缓存命中后仍可能附带跨服务或数据库访问。
- **优化内容**：稳定详情直接使用缓存对象，票档和 UV 等工作分开处理。
- **评估范围**：这是详情接口的数据，还应关注整页请求量和完成时间。

- [ ] **Q88：签到查询的优化为什么主要是减少 Redis 往返，而不是位运算本身？**

检查一个 bit 几乎不费什么计算，贵的是为每一天都去问一次 Redis。优化后一次拿到某个月的位图，在本地完成多项统计，需要跨月时再读对应月份，同一请求不会反复读取同一个月。**因此收益来自减少网络 RTT，不是把简单位运算变成了什么新算法**。如果把登录鉴权也算进去，典型单月请求还有会话读取和续期，通常总共约三次 Redis 操作，不能只报业务部分的一次 GET。

- **主要成本**：逐日 GETBIT 会不断跨网络，位运算本身通常很轻。
- **当前方式**：请求内按月份读取 byte[] 并复用，本地计算当月与连续天数。
- **完整口径**：典型单月查询仍包含会话读取和续期，不能宣传整个请求只有一次 Redis 操作。

- [ ] **Q89：为什么要区分冷启动、稳态、P95、P99 和少量耗时样本？**

第一轮经常包含建连接、JIT 和缓存预热，直接拿它跟另一轮热缓存结果比，很容易把预热当成优化。所以要固定场景，多跑几轮，冷启动和稳态分别报告。延迟也不能只给平均值，用户可能更受尾部慢请求影响。项目里少量异步建单观察值大约在 225 到 278 毫秒，但只有 3 个样本。**它只能说明观察到的例子，不能算出可信的 P99，更不能据此承诺所有订单都在这个时间内完成。**

- **冷与热不同**：连接建立、JIT、缓存预热会影响首轮结果。
- **吞吐与延迟不同**：平均值可能掩盖尾部慢请求，需要足够样本统计分位数。
- **证据边界**：少量异步落单样本约 225–278 ms，只有 3 个样本，不是 P99 或 SLA。

- [ ] **Q90：用户反馈“抢票一直处理中”，你会怎么排查？**

我会先拿到预约号，判断订单其实已经创建、只是前端没刷新，还是后台真的没有处理完。如果预约一直处理中，就往下看任务有没有被认领、下次重试时间是否异常，消息是否到队列，消费者是不是卡在数据库锁或者连续失败。最后再看是否已经进入失败补偿。**先确定卡在哪一个状态转换，再决定重试或修复**，不直接删 Redis 键或手工改成成功，因为那可能把一个可恢复的问题变成重复建单。

- **先定位请求**：根据预约号关联请求、任务、消息和订单，不只看某台机器日志。
- **分段检查**：受理是否提交、任务是否积压、消息是否发送、消费者是否等待锁或失败。
- **看恢复状态**：确认 FAILED、release_pending 和补偿队列，避免先手工改状态掩盖现场。

## 10｜部署、故障场景与面试收尾

- [ ] **Q91：项目怎么部署？数据库初始化和版本升级有什么区别？**

项目使用 Docker Compose 组织应用和中间件，应用包括前端、网关、核心服务和订单服务。部署时不是“容器启动了”就结束，还要确认依赖连接、健康检查以及网关路由都正常。数据库则要特别区分第一次启动和后续升级：**初始化 SQL 只负责新数据目录的建库建表，不能当作每次发布都会执行的迁移工具**。

- **应用运行**：后端采用多阶段构建，运行镜像使用 Java 17，以非 root 用户运行；中间件和应用配置分开管理。
- **首次初始化**：新的数据库数据目录可以执行初始化脚本；已有数据卷不会因为重新启动容器就自动升级表结构。
- **版本升级**：生产环境需要另行设计可追踪的数据库迁移、兼容性检查和回滚方案，不能依赖删数据卷重新初始化。
- **健康检查**：能帮助判断实例是否具备基本服务能力，但不等于整个交易链路已经经过故障验证。

- [ ] **Q92：支持多实例部署，就等于实现高可用了吗？**

不等于。多个应用实例主要是避免业务都压在一个进程上，也能降低单个应用进程退出的影响。但如果所有实例连接的还是同一个 MySQL、Redis 和 RabbitMQ，这些中间件故障时，多启动几份应用也救不了。**应用可横向扩展，和整套系统高可用，是两个层次**。项目具备多实例部署的设计与验证脚本，不能因此包装成已经完成中间件容灾。

- **当前形态**：应用可以多实例运行，Compose 中的 MySQL、Redis、RabbitMQ 和 Nacos 仍是单节点配置。
- **跨主机要求**：注册到 Nacos 的地址必须对其他主机可达，还需要合适的外部流量入口或负载均衡。
- **共享资源**：本地上传目录不会因为应用多实例而自动共享，需使用共享存储或对象存储并统一访问方式。
- **后续建设**：中间件复制、自动故障转移、备份恢复和故障演练，都需要单独配置和验证。

- [ ] **Q93：CI 做了哪些检查？构建镜像和自动部署有什么区别？**

CI 主要帮我在合并和发布前自动检查代码，而不是替我完成生产部署。项目会执行后端测试以及前端构建和测试；主分支检查通过后，再构建后端和前端镜像并推送到镜像仓库。**镜像推送成功只说明产生了可部署产物，不代表线上已经更新**，后面的配置、数据库变更、切流和回滚仍然是部署阶段的工作。

- **检查内容**：PR 和主分支推送触发后端 Maven 测试，以及前端依赖安装、构建和测试。
- **发布产物**：主分支检查通过后，发布三个后端镜像和一个前端镜像，使用提交 SHA 与 latest 等标签。
- **测试与打包**：镜像构建阶段跳过测试，不代表整个流水线跳过测试；检查在独立阶段执行。
- **能力边界**：当前流程不等于自动生产部署，也不能把镜像发布说成已有灰度发布或自动回滚。

- [ ] **Q94：如果准备上线，哪些安全配置需要优先检查？**

我会先检查容易让测试环境直接暴露到公网的配置，而不是先追求更多中间件。比如默认账号、内部共享密钥、Nacos 访问控制、数据库和 Redis 端口，都不能沿用方便本地调试的开放方式。然后检查请求鉴权、日志脱敏和上传资源访问范围。**能在本地跑通，与能安全上线之间还有一组必须明确验收的条件**，这些不能靠一句“使用了 Token”代替。

- **密钥与网络**：使用独立强凭证并做好轮换，限制中间件和内部接口的网络可达范围；不要把密钥写进代码或公开日志。
- **入口安全**：配置 HTTPS、正确的跨域策略和受信任代理头；共享内部 Token 不能替代网络隔离。
- **中间件配置**：当前 Nacos 开发式配置不应直接暴露，需明确开启和验证认证、授权及访问限制。
- **业务边界**：真实支付、退款、短信服务和生产风控尚未完整接入，不能按商业售票系统的能力对外承诺。

- [ ] **Q95：如果再给你两周，你最想改进项目的哪些地方？**

我会先补正确性和恢复链路，再做可观测性，最后根据证据优化性能。现在最值得优先处理的是：Lua 已预扣但预约没有入库时，孤儿占用清理只有启动扫描，存在长期遗留的窗口；其次是补偿失败队列缺少自动修复闭环。**先把失败后能不能收敛讲清楚，比再提高一点入口 QPS 更重要**。

- **第一优先级**：增加周期性的孤儿占用检查，仍要校验预约归属、数据库状态和安全时间窗，避免误释放正在受理的请求。
- **第二优先级**：为补偿失败、长期 PROCESSING 和 release_pending 增加告警、对账与有审计的重放入口。
- **明确的功能风险**：补充 Feed 同分游标的回归测试；完善点赞双写、Feed 投递和 GEO 初始化标记的归属保护。
- **验证方式**：每个改动配一个失败或并发场景测试，再进行稳定条件下的性能对比；这些是改进计划，不是已实现能力。

- [ ] **Q96：旧预约的消息在新预约之后才到，怎么避免状态被覆盖？**

假设用户第一次预约已经失败或取消，随后又发起第二次预约，这时候第一次的旧消息才到，系统不能让旧流程“复活”。创建消息要先检查它对应的预约状态，终态预约不能重新建单；释放消息则要确认 Redis 当前占用还是不是这个预约。**旧消息可以重试，但只能处理自己的生命周期，不能越过状态边界修改新预约**。

- **创建保护**：锁定旧预约并核验状态、订单号、用户和交易快照，不因消息再次到达就重新进入创建流程。
- **释放保护**：比较 reservationId，只有归属相符时才释放 Redis 占用，不能只按用户和票档删除。
- **防重复副作用**：已经存在的订单走幂等处理；已经释放的预约不能再次增加库存或返还积分。
- **测试场景**：先结束旧预约，再创建新预约，最后投递旧创建和旧补偿消息，检查新状态是否保持不变。

- [ ] **Q97：只剩最后一张票，两名用户同时抢，完整处理过程是什么？**

正常情况下，两个人同时抢最后一张票，Redis 的 Lua 会串行完成判断和扣减：一个请求占到名额，另一个看到售罄。但这只能解释正常入口，不能证明异常时永远正确。假如缓存重建等情况使多个请求都进入后续处理，数据库仍会检查库存大于 0 才允许扣减。**最终只能有一个事务成功拿到这张库存，失败方不能继续生成有效订单**。

- **入口控制**：Lua 将余量判断、预扣和归属登记放在一次原子执行中；同一预约重试不重复扣减。
- **业务仲裁**：数据库库存行锁还要协调候补优先级，不是任何进入后续流程的请求都有最终资格。
- **最终防线**：MySQL 条件扣减、有效订单唯一约束，以及订单和积分的本地事务，共同限制最终结果。
- **失败处理**：没能完成创建的预约按状态进入失败和补偿，释放必须校验归属，不能把别人持有的最后一张票加回去。

- [ ] **Q98：为什么选 RabbitMQ 加任务表？同步下单、Redis Streams 或分布式事务能替代吗？**

这些方案可以比较，但不能只按技术新不新来选。同步下单最直观，规模不大时也更容易维护；异步方案更适合把入口受理和后台处理分开，但必须解决状态查询和故障恢复。项目选择 RabbitMQ 加数据库任务表，是让消息投递与业务待办各有依据。**换一种队列，或者接入分布式事务框架，都不会自动消除重复处理、幂等和补偿问题**。

- **同步下单**：链路短、结果直接，但更多工作留在请求线程里，高峰延迟和热点竞争需要评估。
- **Redis Streams**：能够提供消费组与待确认消息管理，但仍需处理消息恢复、业务幂等以及 Redis 运维，不能因为已使用 Redis 就认为替换没有成本。
- **Outbox 思路**：项目任务表与业务记录同事务保存，避免只在内存中记住待办；不代表 MySQL 和 MQ 原子提交。
- **分布式事务**：订单、库存和积分已在同一交易库里，优先使用本地事务；引入额外框架前，先确认它真正覆盖了哪些资源和失败窗口。

- [ ] **Q99：你会给这个项目增加哪些监控、告警和对账指标？**

我会优先监控用户能感受到的业务停滞，而不只是 CPU 和内存。比如接口很快返回了预约号，但预约十分钟还在处理中，入口 QPS 再漂亮也没有意义。所以要跟踪预约从受理到建单用了多久，有多少任务一直重试，取消后的资源是否及时释放。**这里说的是应该补充的观测方案，不能把已有日志说成已经建成了完整监控平台**。

- **入口与完成率**：分别统计受理、预期拒绝、系统异常和最终建单，避免把所有 HTTP 200 都算成下单成功。
- **任务与消息**：关注最老待办年龄、重试次数、线程池拒绝、MQ 积压、死信与补偿失败数量。
- **交易状态**：关注 PROCESSING、release_pending、过期未取消和候补 ALLOCATING 的停留时间，按业务设定告警阈值。

- [ ] **Q100：请用三分钟介绍项目的核心设计、优化结果和不足。**

Ticket Center 是一个演出票务预约项目，覆盖活动浏览、抢票、异步建单、模拟支付、超时取消、积分签到和候补。我想重点解决的是：**库存有限时，既能承受集中请求，又能在重复调用和中途故障以后留下正确的交易结果**。

架构上，用户、活动和互动放在核心服务，预约、订单、库存和积分放在订单服务。交易相关数据保留在同一个数据库里，这样扣库存、扣积分和创建订单可以使用本地事务，不为了拆服务而把强关联操作拆散。

抢票入口先用 Redis Lua 预扣，售罄请求尽早返回。通过后，把预约和待执行任务一起存进 MySQL，再用 RabbitMQ 异步建单。消费者会检查预约状态、消息快照和已有订单，数据库还有条件扣库存与唯一约束。取消时先提交数据库变化，再通过可重试任务释放 Redis 占用。

性能方面，历史本地压测中，预约入口稳态大约从 223 提升到 728 QPS，活动详情大约从 1376 提升到 2511–3584 QPS。预约的数字包含预期业务拒绝，详情的数字只代表该接口，**我不会把它们包装成生产容量或每秒成功成交量**。

这个项目也有清楚的不足：支付是模拟流程，中间件还是单节点；孤儿占用的周期清理、补偿失败的处理闭环和互动功能的一致性还需要完善。如果继续做，我会先补恢复与对账，再根据观测结果优化性能。
