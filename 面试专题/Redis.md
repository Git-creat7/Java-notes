# 基础

> [!question]- Redis 的使用场景有哪些？
> **总**：Redis 是高性能内存键值数据库，主打"读多、要求快、可丢/可过期"的数据，核心场景是缓存，同时覆盖会话、排行榜、分布式锁、消息队列、UV 统计等。
>
> **分**：
> - **缓存**：热点数据、详情页、列表页（Cache-Aside）
> - **会话**：登录 token、验证码（`login:token:*`、`sms:code:*`）
> - **排行榜**：ZSet 按 score 排序
> - **计数器**：点赞、库存、访问量（`INCR` / `DECR`）
> - **分布式锁**：`SET key uuid NX EX`（见 [[分布式锁]]）
> - **消息队列**：List / Pub/Sub / Stream（见 [[消息队列]]）
> - **UV 统计**：HyperLogLog，固定 12KB
> - **签到**：BitMap，1 bit 一个状态
> - **附近商户**：GEO，ZSet + GeoHash
>
> > [!tip] 一句话
> > 凡是"读多、要求快、可丢/可过期、要横向扩展"的数据都适合用 Redis；MySQL 才是真相，Redis 做加速。

> [!question]- Redis 是单线程的，为什么还那么快？
> **总**：因为瓶颈在内存和网络而非 CPU，单线程省掉了多线程的上下文切换、加锁、线程同步开销，再配合 I/O 多路复用和高效数据结构，所以快。
>
> **分**：
> 1. **纯内存操作**：读写不走磁盘，纳秒级
> 2. **单线程无竞争**：省去上下文切换、加锁、线程同步的开销
> 3. **非阻塞 I/O 多路复用**：单线程用 epoll 同时监听大量 socket，命令排队串行执行
> 4. **高效数据结构**：字典 O(1)、跳表、压缩表、整数集合
>
> > [!note] 补充
> > Redis 6.0 之后引入多线程处理**网络 I/O**（读写 socket），但**命令执行仍是单线程**——所以"单线程"主要指执行命令。

# 缓存

> [!faq] 穿透 / 击穿 / 雪崩，一句话区分
> - **穿透**：查**根本不存在**的数据，缓存拦不住
> - **击穿**：**热点 key** 刚好过期，并发全打 DB
> - **雪崩**：**大批 key** 同时过期，或 Redis 挂了

> [!question]- 什么是缓存穿透，怎么解决？
> **总**：穿透是查询缓存和数据库里都**不存在**的数据，存储层查不到也不写缓存，导致每次请求都直打 DB、可能把 DB 打挂，大概率是遭到了攻击；核心思路是让"不存在"也能被缓存或拦截住。
>
> **分**：
> - **缓存空对象**：查不到也写缓存（`""` + 短 TTL，如 2 分钟），下次不查库
> - **布隆过滤器**：不存在的 id 直接拦截，连缓存都不用查
> - 参数校验（类型、范围）、增强 id 复杂度、限流
>
> > [!warning] 空对象的坑
> > 空对象必须写 `""`（blank），不能写 `"null"`——否则 `isNotBlank` 为 true，会误进 `toBean`。

> [!question]- 什么是布隆过滤器？
> **总**：用于判断元素"是否在集合中"，底层是位图 + 多个哈希函数，以少量误判换取极省内存；能判定"一定不存在"，是防穿透的主力。
>
> **分**：
> - **实现**（Redisson）：初始化一个较大的位数组，位都是 0/1；key 进来经 3 次 hash 模数组长度得到下标，把对应位从 0 改 1，用多个位标记一个 key 存在；查询同理
> - 判**不存在** → 直接拒绝，不查缓存、不查库
> - 判**可能存在** → 走正常缓存查询（可能误判，但不会误杀"一定不存在"）
>
> | 优点 | 缺点 |
> | --- | --- |
> | 省内存、拦截无效 id 强 | 有假阳性（误判率可调，通常 < 5%）；元素删除麻烦；要提前灌合法 id |
>
> > [!note] 误判率
> > 误判必然存在，只能靠增大数组长度降低；5% 以内一般项目可接受，不至于高并发压垮数据库。

> [!question]- 什么是缓存击穿，怎么解决？
> **总**：击穿是**设置了过期时间的热点 key** 刚好到期，恰好大量并发请求发现缓存过期，都去 DB 加载并回设，大并发瞬间把 DB 压垮；核心是"同一时刻只让一个请求重建缓存"。
>
> **分**：两种解法
>
> | | 互斥锁 | 逻辑过期 |
> | --- | --- | --- |
> | 做法 | 缓存失效时不立即 load DB，先 `SETNX` 设互斥锁，拿到锁才查库回写，拿不到就重试 get 缓存 | 存 value 时把过期时间字段一起写入、不给 key 设 TTL；查询时判断过期，过期则开一个线程异步同步，当前线程先返回旧数据 |
> | 优点 | 无额外内存、一致性强、实现简单 | 无需干等、吞吐更好 |
> | 缺点 | 等待影响性能；锁要等，可能死锁 | 额外内存、实现复杂、数据同步做不到强一致 |
>
> > [!tip] 权衡
> > **强一致性** → 选互斥锁（性能稍低、锁要等、可能死锁）；**高可用 / 高性能** → 选逻辑过期（性能高、可接受短暂旧数据）。生产锁优先 Redisson。
>
> 互斥锁要点：`tryLock` 用 `setIfAbsent(key, val, 10s)`（SETNX + TTL）；拿到锁后**双重检查**；`finally` 里**只有自己持锁才 unlock**，否则误删别人的锁。

> [!question]- 什么是缓存雪崩，怎么解决？
> **总**：雪崩是**设置缓存时用了相同的过期时间**，导致大量 key 在某一时刻同时失效，请求全部转发到 DB、瞬时压力过重；与击穿的区别——雪崩是很多 key，击穿是某一个 key。
>
> **分**：
> - **TTL 加随机值**：在原有失效时间基础上加随机值（如 1~5 分钟），降低过期时间重复率，很难引发集体失效
> - **Redis 集群 / 主从**：提高服务可用性
> - **降级、限流**：作为系统保底策略，适用于穿透、击穿、雪崩
> - **多级缓存**（本地 + Redis）

> [!question]- redis 作为缓存，MySQL 的数据如何与 Redis 同步？（双写一致性）
> **总**：分场景——要求强一致、时效性高，用 **Redisson 读写锁**；允许一定延时（符合大部分业务），用 **Canal 监听 binlog** 异步同步，不用改业务代码。
>
> **分**：
>
> **方案一：读写锁（强一致）**
> - **读**加**共享锁**：读读不互斥、读写互斥
> - **写**加**排他锁**：读写、读读都互斥，写的同时不让任何线程读，避免脏数据
> - **关键**：读方法和写方法必须用**同一把锁**
> - 排他锁底层就是 `SETNX`，保证同时只有一个线程进入锁住的方法
>
> **方案二：Canal 监听 binlog（最终一致，适合允许延时的业务）**
> - 部署一个 Canal 服务，**伪装成 MySQL 的从节点**，不用改业务代码
> - MySQL 数据更新后，Canal **读取 binlog**，通过 Canal 客户端获取数据，更新缓存
>
> > [!note] 为什么不用延迟双删？
> > 延迟双删 = 先删缓存 → 更新数据库 → 延时再删缓存。延时多久不好确定，过程中有脏数据，不能保证强一致性，所以没采用。
>
> | 方案 | 一致性 | 改业务代码 | 适用 |
> | --- | --- | --- | --- |
> | **读写锁** | 强一致 | 要 | 时效性要求高 |
> | **Canal 同步** | 最终一致 | 不用 | 允许一定延时的大多数业务 |

# 过期与淘汰

> [!question]- Redis 的数据过期策略有哪些？
> **总**：Redis 采用**惰性删除 + 定期删除**两种策略配合使用。
>
> **分**：
>
> **惰性删除**：设置该 key 过期时间后不去管它，当需要该 key 时再检查是否过期，过期就删掉，反之返回该 key。
>
> **定期删除**：每隔一段时间对一些 key 进行检查，删除里面过期的 key。定期清理有两种模式：
> - **SLOW 模式**：定时任务，执行频率默认为 10hz，每次不超过 25ms，可通过修改配置文件 redis.conf 的 hz 选项调整这个次数
> - **FAST 模式**：执行频率不固定，每次事件循环会尝试执行，但两次间隔不低于 2ms，每次耗时不超过 1ms

> [!question]- Redis 的数据淘汰策略有哪些？
> **总**：Redis 提供了很多种，可在配置文件中设置，默认是 **noeviction**（不删除任何数据，内存不足直接报错）；其中两个核心概念是 **LRU** 和 **LFU**。
>
> **分**：
> - **LRU（最近最少使用）**：用当前时间减去最后一次访问时间，这个值越大淘汰优先级越高
> - **LFU（最少频率使用）**：统计每个 key 的访问频率，值越小淘汰优先级越高
>
> **项目设置**：`allkeys-lru`——挑选最近最少使用的数据淘汰，把经常访问的 key 留在 Redis 中。

> [!question]- 内存用完了会发生什么？（如何保证缓存都是热点数据）
> **总**：取决于淘汰策略；项目用 `allkeys-lru` 时，淘汰的是最近最少访问的数据，留下的都是热点数据；若默认 `noeviction`，内存不足时写入直接报错。
>
> **分**：
> - **保证热点数据**：数据库 1000 万、Redis 只能缓存 20 万时，用 `allkeys-lru`，淘汰最近最少使用，留下的都是经常访问的热点数据
> - **内存用尽**：默认 noeviction 不删任何数据、写入直接报错；配置淘汰策略则按规则踢 key 腾空间

# 持久化

> [!question]- Redis 的数据持久化策略有哪些？
> **总**：Redis 提供两种持久化方式：**RDB**（快照）和 **AOF**（追加日志）——RDB 恢复快但可能丢数据，AOF 恢复慢但丢数据风险小；项目通常两个都开、互补使用。
>
> **分**：
>
> **RDB（快照）**
> - 把 Redis 内存数据**定时写到磁盘**成一个二进制快照文件；宕机恢复时直接加载
> - **二进制、体积小、恢复快**，但快照间隔间的数据可能丢失
>
> **AOF（追加文件）**
> - 每次写命令都**追加记录**到 AOF 文件；宕机恢复时**重放一遍命令**
> - 恢复慢，但**丢数据风险小**；可通过**刷盘策略**控制丢数据量
>
> > [!note] 刷盘策略（appendfsync）
> > always（每次写都刷盘，最安全）/ **everysec（每秒一次，项目用的这个）** / no（交给系统）。
>
> | 对比 | RDB（快照） | AOF（追加日志） |
> | --- | --- | --- |
> | 内容 | 内存数据的二进制快照 | 记录每条写命令 |
> | 恢复 | 快 | 慢（重放命令） |
> | 数据丢失 | 可能丢快照间隔间的数据 | 每秒刷盘最多丢 1 秒 |
> | 文件 | 小、紧凑 | 大、可重写（BGREWRITEAOF） |
> | 适用 | 备份、灾难恢复 | 数据可靠性要求高 |
>
> > [!tip] 项目实践
> > 两个都用：RDB 保证快速恢复，AOF 保证少丢数据。4.0+ 还可开**混合持久化**（RDB 全量 + AOF 增量），兼顾速度与可靠。

# 分布式锁

> [!question]- Redis 分布式锁如何实现？
> **总**：一句话：**`SET key uuid NX EX` 原子加锁 + value 存唯一 owner + Lua 脚本原子解锁 + TTL 兜底**。
>
> **分**：手写三要素
> 1. **加锁原子**：`SET lock:order:1 <uuid> NX EX 10`——`NX`（`SET if not exists`）保证不存在才设置；因为 Redis 单线程，命令执行后同一个 key 只能被一个客户端持有，直到过期或删除 key。不能 `SETNX` + `EXPIRE` 分两条命令（中间崩溃会留永久锁）
> 2. **value 用唯一 owner**：`uuid + 线程ID`，不能写死 `1`
> 3. **解锁原子**：Lua 脚本比对 owner 再 DEL
>
> ```lua
> -- KEYS[1]=锁key，ARGV[1]=owner
> if redis.call('get', KEYS[1]) == ARGV[1] then
>     return redis.call('del', KEYS[1])
> end
> return 0
> ```
>
> > [!danger] 为什么不能直接 DEL
> > 线程 A 的锁 TTL 到期 → 线程 B 拿到同 key → A 恢复后 `DEL` → **误删 B 的锁**。所以必须先比对 owner 再删。
>
> 为什么需要分布式锁：`synchronized` / `ReentrantLock` 只在单个 JVM 内有效，多实例部署时彼此看不到对方的线程锁，需要一个所有实例共享的协调位（Redis / MySQL / ZK）。

> [!question]- Redis 分布式锁如何合理控制锁的有效时长？
> **总**：核心是"**TTL 兜底防死锁 + watchdog 自动续期防提前释放**"：TTL 保证进程崩溃后锁能释放，watchdog 保证业务没做完锁不被提前释放。
>
> **分**：setnx 自带指令不好控制时长，项目用 **Redisson** 框架解决，四层手段
> 1. **TTL 兜底**：加锁必须带过期时间，进程崩溃后锁最终释放，避免死锁
> 2. **watchdog（看门狗）续期**：Redisson 需要手动加锁，可控制锁的失效时间和等待时间；每隔一段时间检查当前业务是否还持有锁，持有就增加持有时间；业务执行完再释放锁
> 3. **固定 leaseTime / 等待时间**：`tryLock(waitTime, leaseTime, unit)` 设固定时长，业务必须保证在租约内完成
> 4. **高并发下排队自旋**：客户 1 持锁时客户 2 来了并不会马上拒绝，而是自旋不断尝试获取锁，客户 1 释放后客户 2 马上持有，性能得到提升
>
> > > [!note] 区分两个时间
> > > `tryLock(5, TimeUnit.SECONDS)` 的 5 是"**最多等多久拿锁**"，不是锁的持有时间。

> [!question]- redisson 实现的分布式锁是可重入的吗？
> **总**：可以重入，可重入是为了避免死锁——内部判断是不是当前线程持有锁，是就计数。
>
> **分**：
> - 重入内部逻辑：判断是否是当前线程持有的锁，是就计数 +1；释放锁就技术 -1
> - **存储结构用 Hash**：大 key 可按业务定制，小 key 是当前线程的唯一标识，value 是当前线程重入的次数

> [!question]- redisson 实现的分布式锁能解决主从一致性问题吗？
> **总**：不能完全解决，主从切换时可能丢锁；需要额外手段（RedLock / MultiLock）才更稳。
>
> **分**：
> - 线程 1 加锁成功后，master 节点数据**异步复制**到 slave
> - 此时持有锁的 master 宕机，slave 被提升为新的 master，但**锁还没复制过去**
> - 线程 2 来此时可能给新 master 加上同一把锁，出现**两把锁**（两个客户端同时持锁）
> - 缓解：Redisson MultiLock 必须所有节点都加锁成功才算持有，或 RedLock（半数以上节点加锁）

# 事务

> [!question]- 你们用过 Redis 的事务吗？事务的命令有哪些？
> **总**：用过。Redis 事务是**弱事务**——命令打包串行执行、**无回滚**，不能替代数据库事务。
>
> **分**：命令与特点
> ```text
> MULTI      # 开始事务，后续命令入队
> EXEC       # 执行队列里所有命令
> DISCARD    # 放弃事务
> WATCH key  # 乐观锁：key 被改则事务执行失败
> ```
>
> - **无回滚**：命令全部排队执行，某条命令失败不影响其他命令（不像 MySQL 的 ACID）
> - 配合 `WATCH` 实现乐观锁（如秒杀防超卖：WATCH 库存，被改则失败重试）
> - 适合把"多条命令打包一次执行"，不能替代数据库事务
>
> > [!tip] 与 MySQL 对比
> > MySQL 事务完整 ACID；Redis 事务只有"命令串行执行 + WATCH 乐观锁"，无回滚、无隔离级别。

# 集群与高可用

> [!question]- Redis 集群有哪些方案？
> **总**：演进路线：**单机 → 主从复制 → 哨兵（Sentinel）→ 分片集群（Cluster）**，每步解决不同问题。
>
> **分**：
>
> | 方案 | 解决什么问题 | 局限 |
> | --- | --- | --- |
> | 主从复制 | 读写分离、数据备份 | 主挂后要手动切换，无法自动故障转移 |
> | 哨兵 Sentinel | 监控、自动故障转移 | 数据都在一台主节点，容量有限 |
> | Cluster 集群 | 横向扩展、海量数据 | 架构复杂，多 key 跨节点操作受限 |

> [!question]- 什么是 Redis 主从同步？
> **总**：单节点 Redis 并发能力有上限，搭主从集群实现**读写分离**——一般**一主多从**，主节点负责写、从节点负责读，主节点写入后把数据同步到从节点；同步分**全量同步**和**增量同步**两个阶段。
>
> **分**：
>
> **全量同步**（从节点第一次与主节点建立连接时用）
> 1. 从节点请求主节点同步数据，**携带自己的 `replicationid` 和 `offset` 偏移量**
> 2. 主节点判断是否是第一次请求——依据是**主从两者 `replicationid` 是否相同**；不相同就说明是第一次同步，主节点把自己的 `replicationid` 和 `offset` 发给从节点，让从节点与主节点的信息保持一致
> 3. 同时主节点执行 **`bgsave` 生成 RDB 文件**发给从节点去执行；从节点**先把自己的数据清空**，再执行主节点发来的 RDB 文件，这样就保持了一致
> 4. 如果 RDB 生成执行期间**依然有请求到主节点**，主节点会**以命令的方式记录到缓冲区**（缓冲区是一个日志文件 repl_backlog），最后把这个日志文件发给从节点，这样就保证主从完全一致；后期再同步数据都依赖这个日志文件
>
> **增量同步**（从节点服务重启后数据不一致时用）
> - 从节点请求主节点同步数据，主节点判断**不是第一次请求**
> - 不是第一次就**获取从节点的 `offset` 值**，主节点从**命令日志中获取 `offset` 值之后的数据**，发送给从节点进行数据同步
>
> ![全量同步](Redis-2.png)
> ![增量同步](Redis-3.png)
>
> 主从存在**复制延迟**：从节点读到的是稍旧的数据；故障切换时可能丢数据。
>

> >
> > **候选人**：嗯~~，在 Redis 中提供的集群方案总共有三种：主从复制、哨兵模式、Redis 分片集群

> >
> > 全量同步是指从节点第一次与主节点建立连接的时候使用全量同步，流程是这样的：
> >
> > 第一：从节点请求主节点同步数据，其中从节点会携带自己的 replicationid 和 offset 偏移量。
> >
> > 第二：主节点判断是否是第一次请求，主要判断的依据就是，主节点与从节点是否是同一个 replicationid，如果不是，就说明是第一次同步，那主节点就会把自己的 replicationid 和 offset 发送给从节点，让从节点与主节点的信息保持一致。

> >
> > 增量同步指的是，当从节点服务重启之后，数据就不一致了，所以这个时候，从节点会请求主节点同步数据，主节点还是判断不是第一次请求，不是第一次就获取从节点的 offset 值，然后主节点从命令日志中获取 offset 值之后的数据，发送给从节点进行数据同步

> [!question]- 你们使用 Redis 是单点还是集群？用哪种？
> **总**：我们当时使用的是**主从（1 主 1 从）加哨兵**；**尽量不做分片集群**——内存不够时按业务拆成多套独立主从，而不是上分片。
>
> **分**：
>
> **容量规划**
> - 一般**单节点不超过 10G 内存**
> - 如果 Redis 内存不足，则可以**给不同服务分配独立的 Redis 主从节点**（按业务拆）
>
> **为什么尽量不做分片集群**
> - 集群**维护起来比较麻烦**
> - 集群之间的**心跳检测和数据通信会消耗大量的网络带宽**
> - **没有办法使用 lua 脚本和事务**（多 key 跨槽受限）
>
> **选型对比**
> - 单机：实现简单，但没有自动故障转移，宕机即不可用
> - **哨兵（本项目）**：主从 + 监控 + 自动故障转移，容量不变
> - Cluster：分片 + 自动转移，支撑海量数据，代价见上
>
> > [!note] 陷阱
> > 不要把多个单实例客户端包装起来就叫"集群"；也不要把主从当分片集群。集群 = 自动故障转移 + 数据分片 + 横向扩容。
>

> [!question]- 分片集群中数据怎么存储和读取？
> **总**：数据按 **16384 个哈希槽**分布（`CRC16(key) % 16384` 算槽），槽分配到各节点；客户端直连任意节点，跨节点靠 `MOVED`/`ASK` 重定向。
>
> **分**：
> - **数据分布**：Cluster 有 **16384 个哈希槽**，`CRC16(key) % 16384` 算出槽位，槽被分配到各节点
> - **读写**：客户端直连任意节点，key 不在该节点时返回 `MOVED` 重定向（槽迁移时返回 `ASK`）
> - **优点**：数据分散多节点，单节点内存压力小，可水平扩容
> - **局限**：多 key 操作需在同一节点（可用 hash tag，如 `{user1}`，把相关 key 落到同槽）

> [!question]- redis 集群脑裂是什么？怎么解决？
> **总**：master、slave 与 sentinel **处于不同的网络分区**，sentinel 心跳感知不到 master，就选举提升一个 slave 为 master，于是**存在了两个 master**（像大脑分裂一样）；网络恢复后 old master 被降为 slave 并从新 master 同步，导致 **old master 那段时间写入的大量数据丢失**。解决核心是**限制失联旧主的写入**。
>
> **分**：
>
> **脑裂怎么发生的**
> 1. 由于网络等原因，master、slave 和 sentinel 处于不同的网络分区，**sentinel 没能心跳感知到 master**
> 2. sentinel 通过**选举提升一个 slave 为 master**，此时集群里**存在两个 master**
> 3. 客户端**还在 old master 那里写入数据**，新节点无法同步这些数据
> 4. 网络恢复后，**sentinel 将 old master 降为 slave**，再从新 master 同步数据 → **old master 中的大量数据丢失**
>
> **怎么解决**（redis 配置中设置）
> - **最少 slave 节点个数** `min-replicas-to-write`：比如设置至少要有一个从节点才能同步数据
> - **主从数据复制和同步的延迟时间** `min-replicas-max-lag`：达不到要求就**拒绝请求**，就可以避免大量的数据丢失
> - 合理设置哨兵选举参数（quorum），减少误判
>

> [!question]- 怎么保证 Redis 的高并发高可用？
> **总**：首先**搭建主从集群**，再加上**哨兵模式**——哨兵可以实现主从集群的**自动故障恢复**，所以一般项目都会采用哨兵的模式来保证 redis 的高并发高可用。
>
> **分**：
>
> **哨兵（Sentinel）三大作用**
> 1. **监控**：对主从服务持续心跳检测
> 2. **自动故障恢复**：如果 master 故障，Sentinel 会**将一个 slave 提升为 master**；当故障实例恢复后**也以新的 master 为主**
> 3. **通知**：Sentinel 充当 **Redis 客户端的服务发现来源**，当集群发生故障转移时，会**将最新信息推送给 Redis 的客户端**
>
> **两条线**
>
> | 目标 | 手段 |
> | --- | --- |
> | **高可用** | 主从 + 哨兵自动故障转移；Cluster 节点自动切换；持久化（RDB/AOF）防重启丢数据 |
> | **高并发** | 读写分离（主写从读）；分片集群横向扩展；纯内存 + 单线程低开销 |
> | **保护 DB** | 击穿互斥锁/逻辑过期、雪崩 TTL 随机化、降级限流 |
>
> > [!tip] 面试话术
> > 高可用解决"不挂"，高并发解决"扛得住"。先保证不挂（主从 + 哨兵 + 持久化），再谈扩展（分片 + 读写分离），最后是兜底（限流降级）。
>
