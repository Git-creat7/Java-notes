# GEO 附近商户

GEO 用于存储坐标、按距离查询"附近"。

底层是 **ZSet**：

- member 存商户 / 演出的 id
- score 存经纬度按 **GeoHash** 编码后的 52-bit 整数

> [!note] 为什么要编码？
> 编码后相邻区域的数值也接近，ZSet 按 score 排序才能等价于按距离排序。

## 常用命令

```shell
# member 只存 id：详情回查 DB 拿最新数据，也省内存
GEOADD tc:event:geo:1 116.48105 39.996794 1001

# 按坐标查附近，带距离、按距离升序
GEOSEARCH tc:event:geo:1 FROMLONLAT 116.48 39.99 BYRADIUS 5 km WITHDIST ASC COUNT 10
```

## 项目实践：懒加载 + 分布式锁

GEO 数据不在 Redis 时，从 DB 按分类加载写入，用"分布式锁 + 双重检查"防止并发重复加载：

1. 有 key 直接返回
2. `setIfAbsent` 抢锁（TTL 10s 兜底防死锁）
3. 拿到锁后**再次** `hasKey` —— 双重检查，等锁期间可能别人已经加载完
4. 查 DB 该分类下全部上架数据，`geo.add(key, Map<id, Point(x, y)>)`

查询侧用 `GEOSEARCH ... includeDistance().limit(end)` 取回，在**内存里截取当前页**。

> [!warning] 坑
> - `limit(end)` 是"取前 end 条再内存分页"，深翻页时每页都重复拉前 N 条
> - DB 新增数据不会自动进 GEO，靠懒加载或更新时删 key 触发重建
> - 距离查询只返回 id，详情由 `listByIds` 批量回查

# BitMap 签到

BitMap 是字符串类型的"位数组"视图，**1 个 bit 记录一个二元状态**。

内存账：1 亿用户一天的签到 ≈ 12MB。

## 命令

```shell
SETBIT key offset 1        # 置 1（offset 从 0 开始）
GETBIT key offset
BITCOUNT key               # 统计 1 的个数（本月签到总天数）
BITFIELD key GET u26 0     # 取从第 1 位起的 26 位无符号数（算连续签到用）
```

## 项目实践

key 按月隔离：`tc:sign:{userId}:{yyyyMM}`。

**offset = dayOfMonth - 1**：offset 从 0 起，当月第 N 天存第 N-1 位。

签到：

```java
stringRedisTemplate.opsForValue().setBit(dayKey, dayOfMonth - 1, true);
```

连续签到：

```java
// 取"本月 1 号到今天"的签到情况拼成的二进制数
List<Long> res = stringRedisTemplate.opsForValue().bitField(dayKey,
        BitFieldSubCommands.create()
                .get(BitFieldSubCommands.BitFieldType.unsigned(dayOfMonth))
                .valueAt(0));

// 从最低位（今天）往高位数连续 1 的个数
int count = 0;
while ((num & 1) != 0) { count++; num >>>= 1; }
```

> [!tip] 算法理解
> BITFIELD 拼出的二进制数：**最低位是今天**，往高位依次是昨天、前天……
>
> 所以末尾连续 1 的个数 = 截至今天的连续签到天数 —— 某天没签，那个 0 就截断了连续性。

> [!warning] 坑
> - offset 必须 `day - 1`
> - BITFIELD 结果要判 null / 空（当月无签到时）
> - 跨月的连续签到算不了（key 按月拆分，需要再结合上月末尾几位）

# UV 统计（HyperLogLog）

UV（独立访客数）= 去重计数。三种方案对比：

| 方案 | 精度 | 内存 | 回查明细 | 适用 |
| --- | --- | --- | --- | --- |
| Set | 精确 | O(访客数)，海量时不可接受 | 能 | 小规模，且要知道"谁来了" |
| BitMap | 精确 | 用户量 / 8 字节（1 亿 ≈ 12MB） | 能 | 用户 id 是数字且稠密 |
| **HyperLogLog** | **约 0.81% 误差** | **固定 ~12KB** | 不能 | 海量 UV，只要总数 |

```shell
PFADD tc:uv:event:1 user1 user2 anon-xxx
PFCOUNT tc:uv:event:1          # 去重后的估算基数
PFMERGE total uv:day1 uv:day2  # 合并多天 / 多实例的 HLL
```

项目实践：演出详情页的"想看人数"。

访客标识：登录用 `userId`，未登录用 `anon-{UUID}` —— HLL 只负责去重，不要求真实身份。

> [!question] 面试常问：签到为什么不用 HLL？UV 为什么不用 BitMap？
> 签到需要**按天定位 + 连续性计算**（BITFIELD 按位读），HLL 只能给总数。
>
> UV 用 BitMap 也行（还精确），但访客含匿名 IP / URL 时 BitMap 没法直接用；HLL 无论多少访客都只占 12KB，代价是 0.81% 误差 —— 统计展示值完全够用。

## 三种结构一句话

- **GEO**：ZSet + GeoHash，存坐标查附近
- **BitMap**：位数组，1 bit 一个状态，签到 / 活跃统计
- **HyperLogLog**：固定 12KB 的去重计数器，只要总数不要明细
